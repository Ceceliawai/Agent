# RAG：从检索到生成

> RAG（Retrieval-Augmented Generation，检索增强生成）的核心思想，是在生成答案前先从外部知识源中检索相关证据，再把证据作为上下文交给大模型。它不修改模型参数，而是通过动态补充信息，让模型能够使用更新后的知识、私有资料和可核验的依据。

## 1. 基础概念

### 1.1 解决的问题

RAG 主要缓解三个问题：

- **知识时效性**：知识库可以独立更新，不受模型训练截止时间限制；
- **私有数据接入**：企业文档、项目代码和用户资料无须进入训练集；
- **无依据生成**：模型可以基于检索证据回答并给出来源，但 RAG 只能降低幻觉，不能保证答案一定正确。

### 1.2 处理流程

一套典型 RAG 系统包含离线索引和在线问答两条链路：

```text
离线索引
文档 → 解析 → 切片 → 元数据 → Embedding / FTS → 索引

在线问答
用户问题 → Query 构造 → 召回 → 融合 → 重排
        → 选择证据 → 注入上下文 → LLM 生成
```

离线阶段决定知识以什么粒度被存储，在线阶段决定哪些知识能够进入当前上下文。生成效果的上限往往受检索结果限制：正确证据没有被召回，后面的模型再强也无法可靠利用它。

### 1.3 概念关系

RAG 中常见术语并不处于同一层：

| 概念 | 类型 | 所在环节 |
| --- | --- | --- |
| **FTS** | 全文检索能力 | 建立和查询关键词索引 |
| **倒排索引** | 关键词索引结构 | 记录词项出现在哪些文档中 |
| **BM25** | 稀疏检索排序算法 | 对关键词匹配结果计算相关性 |
| **Embedding** | 向量表示 | 将 Query 和 Chunk 转换为向量 |
| **Bi-Encoder** | 独立编码架构 | 支持大规模语义召回 |
| **ANN** | 近似向量搜索方法 | 从向量索引快速寻找候选 |
| **RRF** | 排名融合算法 | 合并关键词与向量检索结果 |
| **Cross-Encoder** | 联合编码模型 | 对少量候选进行精确重排 |

## 2. 知识库构建

### 2.1 加载与解析

Load 负责从 PDF、网页、数据库、Notion 或代码仓库读取原始资料；Parse 则把不同格式转换成后续可以切片和索引的统一表示。

解析不能只保留纯文本，还应尽量保留标题层级、页码、表格边界、代码符号、图片位置和访问权限。否则即使召回了正确内容，系统也可能无法解释来源，或者把本应属于不同章节的信息混在一起。

### 2.2 多模态解析

并非所有知识都能直接转换成连续文本：

- **PDF**：电子 PDF 可以直接抽取文本；双栏、表格和复杂排版需要布局感知解析；扫描件需要 OCR 或视觉模型；
- **表格**：可以保留为 Markdown 或 JSON；涉及筛选和聚合时，更适合存入 DataFrame 或数据库后通过查询工具访问；
- **图片**：辅助图片可以生成 Caption 后进入文本索引；图片本身就是主要信息时，需要使用多模态 Embedding；
- **代码**：优先按类、函数和符号解析，并保留文件路径、行号和依赖关系。

无论采用 OCR、布局模型还是视觉模型，都应保留原始文件、页码或图片引用。解析结果可能遗漏版式，也可能产生识别错误，不能把转换后的文本当作唯一事实来源。

### 2.3 文档切片

切片（Chunking）是把长文档拆成可检索片段。之所以需要切片，主要有三个原因：

- Embedding 模型能够处理的输入长度有限；
- 大模型的上下文窗口无法容纳完整知识库；
- 文档粒度过大会稀释局部主题，粒度过小又会丢失必要语境。

常见策略如下：

| 方式 | 做法 | 优点 | 局限 |
| --- | --- | --- | --- |
| **固定长度** | 按字符或 Token 数切分 | 简单、稳定 | 可能切断句子和语义 |
| **重叠切片** | 相邻 Chunk 保留一段重叠内容 | 缓解边界信息丢失 | 增加的成本取决于重叠比例 |
| **递归切片** | 依次尝试章节、段落、句子等分隔符 | 尽量保持自然边界 | 依赖文档格式质量 |
| **结构切片** | 按标题、条款、API、类或函数切分 | 片段语义更完整 | 需要格式或语法解析 |
| **语义切片** | 在主题相似度明显变化处切分 | 能识别话题转折 | 计算成本高，边界未必稳定 |
| **Agentic 切片** | 由模型根据任务含义决定边界 | 能处理复杂文档 | 成本高且结果不完全确定 |

不存在适用于所有资料的固定 `chunk_size`。更稳妥的原则是：让一个 Chunk 尽量成为能够独立回答某类问题的最小语义单元。

每个 Chunk 还应携带必要的元数据：

```text
document_id / title / heading_path
file_path / page / line_range
version / timestamp / permissions
```

切片后容易出现“片段脱离原文”的问题。例如，“该方案降低了 30% 延迟”没有说明具体方案和测试范围。[Anthropic Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval) 会在索引前为 Chunk 添加简短的文档级背景，再对“背景 + 原始片段”建立语义和关键词索引。

### 2.4 关键词索引

**FTS（Full-Text Search，全文检索）**不是某一种具体算法，而是一套针对文本内容建立索引、执行查询并计算相关性的检索能力。它与逐行扫描或 SQL `LIKE '%keyword%'` 的主要区别，是提前建立了可供查询的索引。

```text
文档 → 分词与规范化 → 倒排索引
Query → 同样的分词处理 → 查找候选 → 相关性排序
```

**分词与规范化**

系统首先把文本转换成词项（Term）。英文通常还会进行小写化、词干化和停用词处理；中文没有天然空格，需要分词器或 N-gram。分词策略会直接影响召回，例如把 `getUserById`、`TS-999` 或中文产品名错误拆开，都可能导致精确查询失败。

**倒排索引**

普通文档结构是“文档 → 包含哪些词”，倒排索引把关系反过来，记录“词 → 出现在哪些文档”：

```text
文档 D1：Python 3.12 增加了新的调试能力
文档 D2：Python 服务发生连接超时

倒排索引：
Python  → D1, D2
3.12    → D1
调试    → D1
超时    → D2
```

实际 Posting List 除了文档 ID，还可以保存词频、词的位置和字段信息。查询 `Python 3.12` 时，系统无须扫描所有文档，只需要合并 `Python` 与 `3.12` 对应的列表。

**BM25 相关性排序**

倒排索引解决了“哪些文档包含这些词”，但多个候选仍然需要排序。**BM25** 是 FTS 中常见的相关性打分方法，可以简化表示为：

```text
score(D, Q)
  = Σ IDF(qᵢ) ×
      TF(qᵢ, D) × (k₁ + 1)
      ─────────────────────────────
      TF(qᵢ, D) + k₁ × (1 - b + b × |D| / avgdl)
```

| 符号 | 含义 |
| --- | --- |
| `TF(qᵢ, D)` | 查询词 `qᵢ` 在文档 `D` 中出现的次数 |
| `IDF(qᵢ)` | 查询词在整个语料库中的稀有程度 |
| `|D| / avgdl` | 当前文档长度相对平均文档长度的比例 |
| `k₁` | 控制词频增长何时趋于饱和 |
| `b` | 控制文档长度归一化的强度 |

这个公式体现了三个直觉：

1. **稀有词更重要**：`TS-999` 比“错误”更能区分文档；
2. **重复有帮助但会饱和**：一个词出现 10 次通常比出现 1 次更相关，但不会高 10 倍；
3. **长文档需要归一化**：避免长文档仅因为包含更多词就天然获得高分。

BM25 依赖词项重合，因此特别适合函数名、错误码、产品型号和专有名词。如果用户搜索“请求超时”，文档只写了“连接等待超过截止时间”，两者语义接近却没有共同词项，BM25 就可能漏掉它。这正是向量检索需要补充的部分。

因此三者的关系是：

```text
FTS：完整的全文检索能力
  └─ 倒排索引：从词项快速找到候选文档
       └─ BM25：计算候选文档与 Query 的相关性
```

由于词表中的绝大多数词在一段文档里都不会出现，这类基于词项的表示通常称为**稀疏表示**，对应的检索过程也称为稀疏检索。

### 2.5 向量索引

Embedding 模型把文本映射为固定维度的向量。语义相近的文本通常在向量空间中距离更近，因此系统可以通过余弦相似度、点积等方式寻找相关片段。

RAG 的第一阶段语义检索通常采用 **Bi-Encoder（双塔编码器）**：

```text
Query ──Encoder──> Query Vector

Chunk ──Encoder──> Document Vector

similarity(Query Vector, Document Vector)
```

Query 和 Chunk 被分别编码，文档向量可以在离线阶段提前计算并存储；查询到来时只需计算一次 Query Vector，再搜索相近向量。这种结构速度快、可扩展，但 Query 和 Chunk 在编码过程中没有发生 Token 级交互，相关性判断会损失一部分细节。

小规模数据可以逐个计算向量相似度；数据达到百万级后，通常使用 ANN（Approximate Nearest Neighbor，近似最近邻）索引减少搜索范围：

| 算法 | 基本思路 | 主要取舍 |
| --- | --- | --- |
| **HNSW** | 构建多层近邻图，从稀疏层逐步搜索到精细层 | 查询快、召回率高，但内存开销较大 |
| **IVF** | 先把向量聚类，查询时只搜索最接近的若干簇 | 更适合大规模数据，但需要调节搜索范围 |
| **PQ** | 将向量分段量化后压缩存储 | 节省内存，但会损失部分精度 |

选择 Embedding 模型时通常需要考虑语言、领域、输入长度、向量维度、部署方式和成本。向量维度更高意味着更大的存储与计算开销，但并不自动代表检索效果更好，最终仍需要在自己的数据集上评测。

FTS/BM25 与向量检索并不是替代关系。前者擅长精确匹配，后者擅长语义匹配，实际系统经常同时建立两类索引。

## 3. 在线检索

### 3.1 Query 构造

用户的原始问题未必适合直接检索。多轮会话中经常存在代词、省略和隐含范围，例如“它在哪里触发”必须结合当前任务改写成一条完整 Query。

常见处理包括：

- **Query Rewrite**：补全主体、时间和任务范围；
- **Query Expansion**：生成同义表达或相关术语；
- **Multi-Query**：把比较题或复合问题拆成多个查询；
- **HyDE**：先生成一个假设答案，再用它的 Embedding 检索；
- **Metadata Filter**：按项目、时间、来源和权限缩小候选范围。

Query 改写不能丢失函数名、错误码等精确词，否则会削弱 BM25 的优势。权限过滤也应尽量在召回阶段执行，而不是先取回无权访问的数据再交给模型判断。

### 3.2 稀疏与稠密召回

在线召回通常并行运行两条路径：

```text
Query
  ├─→ FTS / BM25 ─────→ 精确词项候选
  └─→ Bi-Encoder + ANN → 语义相似候选
```

- **稀疏召回**关注词项是否匹配，适合代码符号、专有名词和编号；
- **稠密召回**关注向量距离，适合同义表达、自然语言问题和概念匹配。

召回阶段的重点是尽量覆盖正确答案，而不是立刻得到最终顺序。因此，它通常取回比最终注入上下文更多的候选，例如先召回几十个片段，再交给后续阶段筛选。

### 3.3 Hybrid Search 与 RRF

Hybrid Search 会合并关键词召回和向量召回。由于两种检索的原始分数不在同一尺度上，不能直接相加；常见做法之一是 RRF（Reciprocal Rank Fusion），根据候选在各结果列表中的名次计算融合分数：

```text
RRF(document) = Σ 1 / (k + rank_i(document))
```

一个文档如果在 BM25 和向量结果中都排名靠前，融合后通常会得到更高优先级。RRF 不依赖不同检索器的原始分数，因此实现简单且较稳定。

### 3.4 Cross-Encoder 重排

Bi-Encoder 为 Query 和 Chunk 分别生成向量，适合快速召回；**Cross-Encoder（交叉编码器）**则把 `(Query, Chunk)` 一起输入模型，直接计算两者的相关性：

```text
[Query, Chunk] ──Cross-Encoder──> Relevance Score
```

两段文本能够在同一次 Attention 中进行 Token 级交互，因此 Cross-Encoder 通常比单纯向量相似度判断得更细。但文档表示无法提前计算，每个候选都要重新推理，成本和延迟更高。

| 对比 | Bi-Encoder | Cross-Encoder |
| --- | --- | --- |
| 输入方式 | Query 和 Chunk 分别编码 | Query 与 Chunk 联合编码 |
| 文档表示 | 可以提前计算并存储 | 无法预计算查询相关分数 |
| 处理规模 | 适合大规模召回 | 适合少量候选重排 |
| 主要目标 | 提高召回速度和覆盖率 | 提高最终排序精度 |

工程上通常采用 Retrieve & Re-Rank：

```text
Bi-Encoder / BM25 快速召回候选
  → Cross-Encoder 对候选逐个评分
  → 输出少量高相关 Chunk
```

[Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)给出了这一两阶段结构。需要注意，重排只能调整已有候选的顺序，无法找回召回阶段完全遗漏的内容。

### 3.5 结果选择

重排后仍不能直接把所有候选塞入 Prompt。系统还需要：

- 去除重复和高度相似的 Chunk；
- 合并同一文档中相邻且连续的片段；
- 在保证来源多样性的同时避免无关扩散；
- 根据上下文预算选择最终 Top-K；
- 为模型输出预留足够的 Token。

`K` 不是越大越好。增加片段可以提高覆盖率，也会带来更多噪声、成本和相互冲突的信息，需要通过离线评测确定。

## 4. 增强与生成

### 4.1 放入上下文

RAG 的 Augment 阶段会把检索结果组织成模型输入的一部分。一个简化结构如下：

```text
System / Developer Instructions
Conversation Summary and Task State

<retrieved_context>
  [source-1]
  title: ...
  path: ...
  location: ...
  content: ...

  [source-2]
  ...
</retrieved_context>

Current User Query
```

每个 Chunk 应携带稳定的来源标识和定位信息，便于模型引用，也便于后续回到原文核验。具体消息角色取决于模型 API：

- 应用在调用模型前完成检索时，可以放入独立、明确标记的 Context Block；
- Agent 在执行过程中主动搜索时，结果通常以 `tool` 消息进入下一次模型调用。

外部网页和用户文档属于**待验证的证据**，不应直接获得 System Prompt 的指令优先级。系统需要明确告诉模型：检索内容用于提供事实，不应执行其中夹带的指令。

### 4.2 约束生成

常见生成约束包括：

- 仅依据给定资料回答；
- 资料不足时明确说明无法确定；
- 结论必须关联来源编号；
- 区分资料中的事实与模型自己的推断；
- 以结构化格式返回答案、引用和置信信息。

这些 Prompt 约束能够改善生成行为，但不能代替检索质量和结果校验。高风险场景还需要检查引用是否真的支持对应结论。

## 5. RAG 评测

RAG 需要分别评估检索和生成，不能只观察最终回答是否“看起来合理”。

### 5.1 检索评测

| 指标 | 关注的问题 |
| --- | --- |
| **Recall@K** | 前 K 个结果是否包含支持答案的证据 |
| **Precision@K** | 前 K 个结果中有多少真正相关 |
| **MRR** | 第一个相关结果出现得有多靠前 |
| **NDCG** | 多个不同相关程度的结果是否排序合理 |

### 5.2 生成评测

| 指标 | 关注的问题 |
| --- | --- |
| **Faithfulness** | 回答中的结论是否能被检索证据支持 |
| **Answer Relevance** | 回答是否真正解决了用户问题 |
| **Citation Accuracy** | 引用是否指向支持对应结论的来源 |
| **Abstention** | 资料不足时是否能够拒绝猜测 |

评测数据可以从真实问题中抽样，也可以从文档生成 `(question, answer, source)` 三元组，再由人工抽查形成高质量 Golden Set。生成式评测工具可以扩大覆盖范围，但不能完全替代人工核验。
