# 上下文管理

> Agent 之所以看起来能够“记住”任务、连续做出决策并最终完成项目，并不是因为大模型天然拥有长期记忆，而是因为 Agent 在每次调用模型时，都会重新组装一份模型输入。它通常包含 System Prompt、Tool Schema、对话历史和当前用户请求，也可能包含相关代码、工具执行结果以及上一步决策。
>
> 随着任务推进，这些信息会不断累积，但大模型的上下文窗口始终有限。当内容接近或超过窗口上限时，Agent 必须对信息进行选择、裁剪、压缩与重组，在有限空间内保留对后续决策最重要的部分。这个持续维护模型输入的过程，就是上下文管理。

## 1. 基础概念

### 1.1 上下文

大模型的每次调用都可以看作一次独立推理。模型不会自动保留上一次调用的任务状态，也无法直接读取文件系统、工具状态或完整会话；它只能依据当前请求中可见的信息生成结果。

本文所说的**上下文（Context）**，就是 Agent 在一次调用中实际提供给模型，并可被模型用于理解和推理的全部信息。Prompt 是这些信息的载体，而上下文决定了模型此刻“知道什么”。

| 概念 | 含义 |
| --- | --- |
| **上下文** | 当前调用中模型实际可见的信息 |
| **上下文窗口** | 模型一次调用能够处理的 Token 容量，通常需要同时容纳输入和输出 |
| **会话历史** | 任务过程中积累的消息与事件，是构造上下文的信息来源，但不一定全部进入当前调用 |
| **记忆** | 保存在当前上下文之外的信息，需要经过检索或加载才能再次被模型使用 |

因此，Agent 的“记忆”并不等于模型真的记住了过去。只有被保留在对话历史中，或从外部存储重新取回并加入当前请求的信息，才能继续影响模型的判断。

### 1.2 上下文组成

Agent 调用模型时，提交的通常不是一段孤立的用户问题，而是一组经过组织的消息、指令和能力描述。不同框架的具体格式可能不同，但一次典型调用大致包含以下内容：

| 组成部分 | 作用 | 变化特点 |
| --- | --- | --- |
| **System Prompt** | 定义模型的角色、行为边界和核心规则 | 相对稳定 |
| **Tool Schema** | 描述模型可以使用的工具及其参数 | 随可用工具变化 |
| **对话历史** | 提供此前的用户消息、模型回复和工具结果 | 随会话持续增长 |
| **当前用户请求** | 指明当前需要解决的问题 | 每轮变化 |
| **任务状态与相关材料** | 提供目标、计划、代码、检索结果和关键决策 | 按当前任务动态选择 |

可以将它抽象为：

```text
本次模型上下文
  = 系统指令
  + 工具描述
  + 对话历史
  + 当前请求
  + 当前任务所需的状态与材料
```

这些信息不会自动被模型感知。代码文件只有经过读取并放入请求，工具执行结果只有被追加到后续消息，上一步决策只有被历史、摘要或任务状态保留下来，才会成为下一次推理的依据。

不同内容的优先级、生命周期和 Token 成本并不相同：系统指令通常需要稳定保留，对话和工具结果却会不断增长，代码与记忆则应按需加载。上下文管理要解决的核心问题，就是在有限窗口中决定**哪些信息应该进入、以什么形式进入，以及保留多久**。

## 2. 管理策略

上下文管理的目标并不是尽可能填满窗口，而是在有限的 Token 预算内，提高与当前决策相关的信息密度。具体策略可以归纳为两类动作：需要信息时按需扩展上下文，信息过多时主动收缩上下文。

| 策略 | 核心动作 | 适用场景 |
| --- | --- | --- |
| **选择性加载** | 只加载当前步骤需要的信息 | 文件、工具和知识库规模较大 |
| **裁剪与替换** | 删除低价值内容，使用引用或结构化结果代替原文 | 工具输出冗长、重复信息较多 |
| **摘要与压缩** | 将较早过程整理为更短的状态描述 | 长对话和长时间运行的任务 |
| **外部化与检索** | 将完整信息存到窗口之外，需要时再取回 | 跨会话记忆、大型代码库和文档 |
| **上下文隔离** | 为不同任务维护独立上下文 | 子任务、子 Agent 和并行工作流 |

### 2.1 选择性加载

选择性加载不是简单地“少放一些内容”，而是先让模型知道**有哪些信息或能力可用**，再根据当前任务逐级加载细节。这样既保留了发现能力，也避免把所有内容一次性塞进上下文。

#### 2.1.1 工具延迟加载

传统 Agent 会在每次模型调用前注入所有工具的名称、说明和参数 Schema。工具数量较少时这种方式最直接；但当 Agent 同时连接多个 MCP Server 或大型工具集时，即使本轮只使用一个工具，模型也要为全部 Schema 支付 Token 和注意力成本。

[OpenClaw Tool Search](https://docs.openclaw.ai/tools/tool-search) 提供了一种延迟加载机制：

1. 运行时先根据权限和当前环境筛选可用工具；
2. 模型初始只看到一个有界的能力目录，以及 `search`、`describe`、`call` 等入口；
3. 模型根据任务搜索候选工具；
4. 确认候选后，再加载该工具的完整参数 Schema；
5. 最终调用选中的工具。

```text
能力目录
  → search("create a GitHub issue")
  → 返回候选工具
  → describe(tool_id)
  → 加载完整 Schema
  → call(tool_id, arguments)
```

这里被延迟的主要是数量庞大、结构较长的工具定义。文件读写等核心工具，以及必须直接调用的工具，仍可以始终暴露给模型。OpenClaw 当前将 Tool Search 标记为实验能力，因此它更适合作为“选择性工具加载”的实现案例，而不是所有 Agent 都必须遵循的固定接口。

#### 2.1.2 Skill 渐进披露

Skills 解决的是另一类问题：Agent 可以拥有大量领域工作流，但当前任务通常只需要其中一个。如果把所有 Skill 的完整说明都放进 System Prompt，会迅速占满上下文。

[Agent Skills 规范](https://agentskills.io/specification#progressive-disclosure)采用三级渐进式披露：

| 阶段 | 加载内容 | 目的 |
| --- | --- | --- |
| **发现** | 所有 Skill 的 `name` 和 `description` | 让模型知道有哪些能力以及何时使用 |
| **激活** | 被选中 Skill 的完整 `SKILL.md` | 提供当前任务需要的操作流程 |
| **执行** | `references/`、`scripts/`、`assets/` 中的具体资源 | 只在执行到相关步骤时读取或使用 |

```text
Skill 元数据
  → 判断当前任务是否匹配
  → 加载 SKILL.md
  → 按步骤读取 reference 或运行 script
```

OpenClaw 在暴露 Skills 前还会依据配置、操作系统、环境变量和本地依赖进行过滤，只让当前 Agent 看到实际可用的 Skill。这个过程体现了两层选择：运行时先筛掉不可用能力，模型再从可用能力中选择与任务相关的内容。

#### 2.1.3 代码渐进读取

同样的机制也适用于代码库和文档。代码 Agent 通常先通过目录、符号索引或文本搜索定位目标，再读取命中的代码片段；只有理解完整实现确实需要时，才展开整个文件或继续追踪依赖。

```text
目录与符号
  → 搜索命中
  → 相关代码片段
  → 完整文件或依赖实现
```

这三类实现虽然加载对象不同，但都遵循同一个结构：**用低成本的元数据维持可发现性，用按需加载的详细内容支持实际决策。**

### 2.2 裁剪与替换

裁剪用于移除已经失去决策价值的信息，例如重复回复、过期状态、无关日志和过长的工具输出。对于仍需追溯但不必全文保留的内容，可以用文件路径、结果摘要或结构化状态进行替换。

裁剪的依据不应只是“信息是否足够旧”，而应是“它是否仍会影响后续决策”。任务目标、用户约束和尚未解决的问题即使出现得很早，也不能因为超出最近消息窗口就被直接删除。

#### 2.2.1 工具结果清理

工具结果通常是 Agent 上下文中增长最快的部分。一次文件读取可能返回几千行代码，一次测试可能产生大量日志；模型完成判断后，这些原始内容的价值会快速下降，但关键结论仍需要保留。

[Anthropic Context Editing](https://docs.anthropic.com/en/docs/build-with-claude/context-editing) 提供了 `clear_tool_uses` 机制：

1. 在模型请求发送前检查输入 Token 是否超过阈值；
2. 保留最近若干次工具调用，以及配置为不可清理的工具结果；
3. 按时间顺序清理更早的 Tool Result；
4. 使用占位内容替换原始结果，让模型知道这里曾发生过一次工具调用；
5. 客户端仍保存完整历史，改变的只是本次发送给模型的上下文。

```text
完整会话历史
  → 达到清理阈值
  → 保护最近结果和关键工具
  → 旧 Tool Result 替换为占位信息
  → 构造更小的模型输入
```

这里的关键不是简单删除旧消息，而是区分**执行事实**和**原始载荷**。例如，“测试失败，原因是数据库连接超时”可能仍需保留，但几千行完整测试日志可以被清理，并用日志文件路径替代。

#### 2.2.2 裁剪边界

实现裁剪时通常需要保护以下内容：

- 当前仍未完成的 Tool Call 及其 Tool Result；
- 后续决策仍依赖的原始证据；
- 用户明确提出的目标与约束；
- 无法从外部系统重新获取的信息。

因此，裁剪应该作用于模型看到的表层，而不是直接删除系统中的原始记录。否则一旦模型需要核对细节，Agent 将无法恢复被裁掉的信息。

### 2.3 摘要与压缩

裁剪适合处理已经不再需要的原始载荷；如果一段历史仍然包含重要状态，就需要使用压缩，将多轮消息转换为更短但可继续工作的表示。

一次完整的压缩通常包含以下步骤：

```text
监测 Token 使用量
  → 选择已经完成且边界安全的历史
  → 生成结构化摘要
  → 用摘要替换原始历史
  → 重新计算 Token
  → 继续下一次模型调用
```

有效的压缩结果至少需要保留：

- 当前目标与约束；
- 已完成的工作和关键决策；
- 修改过的文件与重要工具结果；
- 已验证的结论与失败尝试；
- 未解决的问题和下一步行动。

#### 2.3.1 压缩实现

[OpenAI Responses API Compaction](https://developers.openai.com/api/docs/guides/compaction) 支持两种触发方式：

- **自动压缩**：配置 `compact_threshold`，当模型输入超过阈值时，由服务端生成 Compaction Item，并在后续请求中携带；
- **主动压缩**：调用 `/responses/compact`，把当前完整上下文转换为新的压缩上下文，再用它继续会话。

返回的 Compaction Item 是面向模型续接状态的压缩结果，不要求人类可读。应用只需要把它作为后续请求的一部分继续传递。

本知识库分析过的 [DSH 上下文压缩](../dsh/compaction) 则展示了另一种实现：系统先剪枝旧的工具结果，如果空间仍然不足，再选择已经完成的历史生成摘要。摘要只替换模型看到的 Model Surface，原始事件仍保留在 Session Event Log 中。

```text
先剪枝工具结果
  → 重新测量
  → 空间仍不足时生成摘要
  → 替换 Model Surface
  → Session Log 保留原始事实
```

压缩通常是有损的，摘要可能遗漏细节，也可能把模型的推测写成事实。因此，系统不应只保存摘要，还应保留摘要覆盖的范围和原始记录引用；当任务需要精确证据时，Agent 才能回到源数据进行核对。

### 2.4 外部化与检索

上下文窗口不适合作为完整信息仓库。Agent 可以把会话事件、代码文件、项目文档和长期记忆保存在外部系统中，当前上下文只保留必要的状态、索引与引用。

```text
写入原始信息
  → 建立索引
  → 根据当前任务检索
  → 对候选结果排序与去重
  → 读取精确内容
  → 注入当前上下文
```

外部化机制包含两个方向：

- **写入**：把完整会话、工具产物、代码文件和稳定结论保存到上下文窗口之外；
- **召回**：根据当前目标找到相关信息，经过筛选后重新注入模型输入。

RAG 是外部信息进入上下文的典型机制：系统先从知识库召回相关证据，再将筛选后的片段注入当前模型请求。完整的切片、Embedding、FTS、BM25、混合召回、Cross-Encoder 重排与生成链路，参见 [RAG：从检索到生成](./rag)。

#### 2.4.1 OpenClaw 记忆检索

[OpenClaw Memory](https://docs.openclaw.ai/concepts/memory) 将记忆保存在工作区的 Markdown 文件中：`USER.md` 保存稳定的用户信息，`MEMORY.md` 保存经过整理的长期事实与决策，日期文件保存更详细的阶段记录。文件是可检查的事实载体，而不是模型内部的隐藏状态。

当记忆规模增大后，[Memory Search](https://docs.openclaw.ai/concepts/memory-search) 会把内容切分并建立索引，检索时同时执行：

```text
当前查询
  ├─→ 向量检索：寻找语义相近的内容
  └─→ BM25 检索：寻找名称、ID 和错误信息等精确词项
          ↓
      合并与排序
          ↓
  相关性 × 时间衰减 × 重要性
          ↓
      去除重复结果
          ↓
       返回 Top-K
```

语义检索适合处理表达方式不同但含义相近的内容，关键词检索则更适合错误码、函数名和配置项。返回候选片段后，Agent 还可以再读取对应文件或行范围，避免只根据模糊检索片段做出最终判断。

这个过程说明，信息被保存并不代表模型已经“记住”。记忆能否真正参与决策，还取决于写入内容是否准确、索引是否及时、查询能否命中，以及召回结果是否经过验证。

### 2.5 上下文隔离

当一个任务包含多个相对独立的子问题时，可以让子 Agent 或独立工作流分别维护自己的上下文。每个执行单元只接收完成局部任务所需的信息，结束后再把结论、证据和未解决问题返回给主 Agent。

隔离的重点不是增加 Agent 数量，而是建立新的上下文边界：

```text
主 Agent
  → 生成完整的子任务说明
  → 子 Agent 在独立上下文中检索和调用工具
  → 中间过程留在子上下文
  → 只返回结论、证据和产物引用
  → 主 Agent 汇总结果
```

[Anthropic 的多 Agent Research 系统](https://www.anthropic.com/engineering/multi-agent-research-system)采用了这种模式。Lead Agent 负责制定研究策略并拆分方向；每个 Subagent 使用独立的上下文窗口搜索和分析资料，再把压缩后的发现返回给 Lead Agent。子 Agent 在这里既是执行者，也是信息过滤器：大量搜索结果停留在局部上下文中，主上下文只接收可以用于最终综合的内容。

隔离是否有效，取决于两次交接：

- **派发任务时**：需要包含目标、范围、已有约束、可用工具和期望输出；
- **返回结果时**：需要包含结论、关键证据、来源、置信度和未解决问题。

如果任务之间高度依赖同一份可变状态，隔离反而会增加同步成本并产生冲突。因此，它更适合可独立探索、会产生大量中间信息、最终结果容易归纳的子任务，而不适合需要频繁共享状态的连续操作。

### 2.6 策略组合

实际系统通常不会只使用一种策略，而是根据 Token 压力逐步升级处理：

```text
平时：选择性加载，只引入当前需要的信息
  ↓
轻度压力：裁剪旧工具结果和重复内容
  ↓
持续增长：压缩已经完成的历史阶段
  ↓
长期任务：把完整事实外部化，并按需检索
  ↓
独立子任务：使用新上下文隔离执行过程
```

每次处理后都需要重新计算 Token，并确认任务目标、用户约束、关键决策和当前状态仍然存在。上下文管理不是简单地“减少 Token”，而是在每次模型调用前重新判断：**下一步决策真正需要哪些信息，这些信息能否在需要时恢复？**

## 3. 内存置换类比

理解上下文管理的一种直观方式，是把它类比成计算机在有限内存与外部存储之间维护 Working Set：

| 计算机系统 | Agent 系统 |
| --- | --- |
| 内存或 Cache | 模型当前的上下文窗口 |
| Working Set | 当前步骤真正需要的信息 |
| 磁盘 | 文件、Session Log、知识库和长期记忆 |
| Page In | 检索并加载文件、Skill、工具 Schema 或记忆 |
| Eviction | 裁剪旧消息、工具结果和无关内容 |
| Compression | 用摘要替换一段原始历史 |
| Page Fault | 模型发现信息不足，再通过工具重新读取 |
| Memory Manager | 负责选择、组装和压缩信息的 Context Manager |

```text
外部存储
  ↓ 检索与加载
当前 Working Set
  ↓ 模型推理
产生消息、决策和工具结果
  ↓ 写回外部存储
达到窗口阈值
  ↓
裁剪、压缩或换出
```

不过，这个类比并不完全等价。模型不能像程序访问内存地址一样随机读取外部信息，内容离开上下文后必须通过检索或工具调用重新加载；操作系统换页通常可以无损恢复，而摘要压缩可能遗漏细节。因此，完整事实仍应保存在可追溯的外部存储中，压缩结果只负责维持当前模型调用所需的工作上下文。
