# 存储系统

## 1. TOS 是分布式存储吗

是。TOS（Torch Object Storage）是一个采用分布式架构实现的对象存储系统。

这里需要区分两个维度：

- **对象存储**描述对外的数据模型：用户通过 Bucket、Key 和 Object 管理数据。
- **分布式存储**描述系统的实现方式：数据和元数据分布在多个节点上，通过分区、冗余和故障恢复实现横向扩展与高可靠。

因此，TOS 既属于对象存储，也属于分布式存储。对象存储并不等于普通文件系统：传统对象存储提供的是扁平命名空间，`images/avatar.jpg` 中的 `/` 通常只是 Key 的一部分，并不一定对应真实目录。

## 2. Bucket 与 Object

TOS 的基本数据模型如下：

```text
TOS
└── Bucket（存储桶，对象的容器和命名空间）
    └── Object（对象，存储数据的基本单元）
        ├── Key（对象在 Bucket 内的完整名称）
        ├── Data（对象内容）
        └── Metadata（大小、类型、创建时间等描述信息）
```

- **Bucket**：存放 Object 的容器，具有地域、访问权限、存储冗余等配置。
- **Object**：对象存储管理数据的基本单元，由 Key、Data 和 Metadata 组成。
- **Key**：Object 在 Bucket 内的唯一标识。它看起来可以像文件路径，但传统对象存储通常把它当作一个完整字符串。
- **Metadata**：描述对象属性，包括系统元数据和用户自定义元数据。

定位一个对象通常需要 `Bucket + Key`。单个 Bucket 的存储空间可以按需扩展，但桶数量、对象大小、Key 长度和 API 请求等仍受产品规格限制，不能笼统理解为“所有维度都无限”。

## 3. 底层如何存储

从使用者视角看，一个 Object 是完整的数据对象；从常见的分布式对象存储实现看，系统会将数据和索引分散到多个节点，并通过冗余机制保证可靠性。

### 3.1 数据分片

大对象在存储层通常会被切分为多个数据块或条带，再根据分区规则放置到不同存储设备或节点：

```text
avatar.jpg
    ↓ 存储层切分
[数据块 1] [数据块 2] [数据块 3] ...
    ↓          ↓          ↓
  节点 A      节点 B      节点 C
```

这样可以把容量和读写压力分散到多台机器，并通过增加节点横向扩展系统。具体的数据块大小、分区算法和放置策略属于产品实现细节，不能仅根据公开 API 假定为固定的 `4 MiB`。

### 3.2 冗余与故障恢复

分布式存储需要允许部分磁盘或节点故障而不丢失数据，常见方案包括：

| 方案 | 原理 | 主要特点 |
| --- | --- | --- |
| 多副本 | 将同一份数据保存到多个故障域 | 读取和恢复简单，但空间开销较大 |
| 纠删码（EC） | 将数据编码为 N 个数据块和 M 个校验块，丢失不超过 M 块时可恢复 | 空间利用率较高，但编码和恢复计算更复杂 |

产品可以根据可靠性、性能和成本目标采用不同策略。TOS 对外公开了单 AZ、多 AZ 等冗余能力，但不能据此直接推断“热数据一定使用三副本、冷数据一定使用纠删码”；具体映射应以官方架构资料为准。

### 3.3 元数据与对象索引

系统还需要维护 Bucket、Key、版本、权限、对象属性以及数据定位信息。概念上的读取链路如下：

```text
客户端请求 Bucket + Key
        ↓
接入层完成鉴权和路由
        ↓
元数据或对象索引定位数据
        ↓
存储节点读取数据块
        ↓
校验并以完整 Object 返回
```

元数据服务本身也需要分区、复制和一致性机制。实际系统通常不会简单地在一条元数据记录中列出每个数据块的位置，而会通过多级索引、分区映射和数据放置规则完成定位。

## 4. 分片上传

分片上传（Multipart Upload）解决的是客户端如何可靠、高效地上传大对象：

1. **初始化**：创建分片上传任务，获得唯一的 `UploadId`。
2. **上传分片**：使用 `UploadId` 和 `PartNumber` 独立上传各个 Part，可以并发执行。
3. **完成上传**：提交所有 Part 的编号和 ETag，由 TOS 生成最终 Object。

```text
CreateMultipartUpload → UploadId
        ↓
UploadPart(1) ─┐
UploadPart(2) ─┼─ 可并发、可单独重试
UploadPart(N) ─┘
        ↓
CompleteMultipartUpload → Object
```

它的主要价值是：

- **失败重试**：某个 Part 失败时只需重新上传该 Part。
- **并行传输**：多个 Part 可以并发上传，提高链路利用率。
- **暂停与恢复**：应用保存 `UploadId` 和已完成 Part 后，可以继续未完成的上传。

需要注意，Multipart 的 **Part 是上传协议中的逻辑分片**，存储层的数据块是服务端内部实现，两者不是同一概念。分片上传也不代表对象大小没有限制；以 TOS 当前规则为例，除最后一片外单片至少为 `4 MiB`，最多包含 `10000` 个 Part，具体限制应以最新产品文档为准。

## 5. 访问控制

TOS 可以通过 IAM 策略、Bucket Policy 和 ACL 等机制控制访问。Bucket 和 Object 通常应保持私有，只给业务身份授予必要权限；公开读适合确实需要匿名访问的公共资源，但会带来数据泄露和流量费用风险。

私有对象需要临时提供给客户端时，可以由可信服务端生成预签名 URL：

```text
https://<bucket>.<endpoint>/<key>?X-Tos-Signature=...&X-Tos-Expires=3600
```

预签名 URL 把指定操作和过期时间包含在签名中，使用者不需要持有长期 AK/SK。它本质上是一段临时凭证，任何获得 URL 的人都可以在有效期内执行签名允许的操作，因此应限制权限和有效期，并避免记录到公开日志。

## 6. 冷热分层

不同存储类型是在访问延迟、最低存储时间、取回费用和存储成本之间做权衡，而不只是简单地将数据划分为“热”和“冷”：

| 类型 | 适用场景 | 访问特点 |
| --- | --- | --- |
| 标准存储 | 高频访问的数据 | 毫秒级直接访问，存储费用较高 |
| 低频存储 | 不频繁访问的数据 | 可直接访问，但通常有最低存储时间和取回费用 |
| 智能分层 | 访问频率难以预测的数据 | 根据访问频率自动转换访问层 |
| 归档闪回 | 很少访问但仍要求直接读取的数据 | 可直接访问，存储成本较低 |
| 归档及更冷类型 | 长期保存、极少读取的数据 | 读取前通常需要恢复，恢复时间和成本更高 |

业务可以在上传时指定存储类型，也可以通过生命周期规则让对象随时间自动转为更冷的类型。

## 7. 面试问答

### TOS 为什么既是对象存储，又是分布式存储

对象存储描述对外接口，分布式存储描述底层架构。TOS 对外以 Bucket、Key 和 Object 组织数据，对内通过分区、冗余和多节点协作提供海量容量与故障恢复能力。

### Key 是真实文件路径吗

传统对象存储通常采用扁平命名空间，Key 是一个完整字符串。`images/avatar.jpg` 看起来具有目录层级，主要是因为控制台和工具按照 `/` 前缀模拟了目录；只有明确启用分层命名空间时，目录才具有更接近文件系统的语义。

### 分片上传和底层数据分片有什么区别

分片上传是客户端协议，用于并发上传、失败重试和断点续传；底层数据分片是服务端存储布局，用于容量扩展、负载均衡和故障恢复。服务端可以再次切分或重新编码上传的 Part。

### 多副本和纠删码如何选择

多副本以更大的空间开销换取简单、低延迟的读取与恢复；纠删码能降低冗余空间，但编码和故障恢复的计算、网络成本更高。具体系统会结合数据规模、访问频率和恢复目标选择，不能仅凭存储类型断言 TOS 的内部方案。

### 预签名 URL 为什么能访问私有对象

服务端使用凭证对操作、资源和过期时间签名。TOS 收到请求后验证签名，在有效期内临时认可该请求，而不需要把长期凭证交给客户端。

## 8. 一句话总结

TOS 是采用分布式架构实现的对象存储：对外使用 Bucket、Key 和 Object 管理数据，对内通过分区、冗余、索引和多节点协作实现扩展与可靠性，并提供分片上传、权限控制、预签名 URL 和冷热分层等能力。
