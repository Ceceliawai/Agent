# 通用基础

## 1. 设计原则：SOLID

SOLID 是面向对象设计中五条常见原则的缩写。它们关注的不是把代码拆得越细越好，而是控制职责、依赖和变化的影响范围，使系统更容易理解、扩展和测试。

### 1.1 单一职责原则（SRP）

单一职责原则指一个类或模块应该只负责一类职责，最好只有一个引起它变化的原因。它的目的不是机械地把类拆得越小越好，而是降低修改的影响范围，提高代码的可维护性、可读性和可测试性。

例如在订单系统中，如果 `OrderService` 同时负责价格计算、库存扣减、订单创建、消息通知和报表统计，它就承担了过多职责。更合适的做法是把价格、库存和通知等逻辑交给独立组件，`OrderService` 只负责下单流程的编排。

### 1.2 开闭原则（OCP）

开闭原则指软件实体应该**对扩展开放，对修改关闭**。当系统增加一种新能力时，应该尽量通过新增实现来完成，而不是反复修改已经稳定的核心流程，从而减少回归风险。

例如支付系统支持支付宝和微信支付时，如果 `PaymentService` 使用一个不断增长的 `if-else` 判断支付类型，那么每增加一种支付方式都要修改它。更合适的做法是定义统一的 `PaymentMethod` 接口，每种支付方式提供自己的实现，核心流程只负责选择并调用对应实现。

### 1.3 里氏替换原则（LSP）

里氏替换原则指子类型必须能够替换父类型，并且不破坏调用方原有的正确性。子类型不仅要满足相同的方法签名，还要遵守父类型承诺的行为，例如输入约束、返回结果和异常语义。

例如系统定义了支持 `save` 和 `get` 的 `Storage`，本地存储和对象存储都应该能够正常实现这两个操作。如果某个只读存储继承 `Storage` 后，在调用 `save` 时直接抛出“不支持”异常，它就不能真正替换父类型。此时应拆分读写接口，而不是建立不恰当的继承关系。

### 1.4 接口隔离原则（ISP）

接口隔离原则指调用方不应该依赖自己不需要的方法。与其设计一个包含大量能力的通用接口，不如按照使用场景拆成多个小而明确的接口，避免一个无关方法的变化影响所有实现者。

例如一个 `UserService` 接口同时包含用户查询、修改、数据导出和邮件发送，仅读取用户信息的调用方也会被迫依赖后面三类能力。可以将它拆成 `UserReader`、`UserWriter`、`UserExporter` 等接口，让调用方只依赖实际使用的部分。

### 1.5 依赖倒置原则（DIP）

依赖倒置原则指高层业务逻辑不应该直接依赖具体的底层实现，高层和底层都应该依赖稳定的抽象。这样底层技术发生变化时，核心业务流程不需要随之修改，也更容易在测试中替换外部依赖。

例如 `OrderService` 如果直接创建某个支付 SDK 的客户端，业务逻辑就会与该供应商绑定。更合适的做法是让它依赖 `PaymentGateway` 接口，再由外部注入具体实现。切换支付供应商或编写单元测试时，只需替换实现，不必修改订单流程。

## 2. 常用设计模式

设计模式是对一类重复设计问题的通用解决方案。它描述对象应该如何分工与协作，而不是一段可以直接复制的固定代码。只有当相应的变化和复杂度真实存在时，使用设计模式才有价值。

### 2.1 工厂模式

工厂模式把**使用对象**与**创建对象**分开：调用方只表达自己需要什么，不直接决定具体类型如何构造。

例如支付系统同时支持支付宝和微信支付，可以让两种支付实现遵守同一个 `PaymentMethod` 接口，再由工厂根据支付类型返回对应实现：

```text
OrderService
    ↓ 请求 paymentType
PaymentFactory
    ├─ alipay → AlipayPayment
    └─ wechat → WechatPayment
```

这样 `OrderService` 不需要知道 SDK 客户端如何初始化，也不负责管理不同支付实现的构造参数。对象创建逻辑发生变化时，业务流程通常不需要修改。

工厂模式有几个常见层次：

- **简单工厂**：由一个工厂方法通过条件判断创建不同对象。实现简单，但新增类型仍要修改工厂；它不属于 GoF 23 种模式。
- **工厂方法**：为每类产品提供相应工厂，通过新增工厂和产品实现扩展。
- **抽象工厂**：负责创建一组相互关联的对象，例如同时创建某个云厂商的存储、消息和监控客户端。

如果对象构造非常简单、实现类型也不会变化，直接创建通常更清楚，不必为了模式额外增加工厂层。

### 2.2 策略模式

策略模式把一组可以互相替换的算法封装为独立实现，调用方通过统一接口使用它们。它解决的是**同一个业务目标存在多种实现方式**的问题。

例如电商系统可能同时存在普通会员、VIP 和促销活动三种计价规则：

```text
PriceService
    ↓ 使用 PricingStrategy
    ├─ NormalPricing
    ├─ VipPricing
    └─ PromotionPricing
```

`PriceService` 只负责调用当前策略，不需要在核心流程中维护不断增长的 `if-else`。具体策略可以由配置、用户类型或工厂在运行时选择。

策略模式与工厂模式经常配合使用，但两者目的不同：**工厂负责创建哪个对象，策略负责执行哪种行为**。如果算法只有一种且没有变化预期，引入策略接口只会增加不必要的间接层。

### 2.3 单例模式

单例模式保证一个类在特定作用域内只有一个实例，并提供统一的获取方式。它适合管理进程内需要共享且创建成本较高的对象，例如配置中心客户端、指标注册器或连接池管理器。

实现单例通常需要处理两个问题：

1. **唯一创建**：构造过程不能被调用方任意执行；
2. **并发安全**：多个线程同时首次访问时，不能创建多个实例。

常见实现包括启动时直接创建的饿汉式、首次使用时创建的懒汉式，以及双重检查锁。双重检查锁还必须依赖语言提供的内存可见性保证；例如 Java 通常需要配合 `volatile`，Go 通常使用 `sync.Once`。

单例也有明显边界：

- 单例对象的创建是线程安全的，不代表它内部的可变状态也是线程安全的；
- 进程内只有一个实例，不代表分布式系统中全局只有一个实例；
- 隐式全局状态会增加测试和并发推理难度，依赖注入容器管理的单例作用域通常更容易控制。

### 2.4 观察者模式

观察者模式在一个对象状态发生变化时，通知所有订阅者执行相应操作。发布者只维护统一的观察者接口，不需要了解每个订阅者的具体逻辑。

例如订单创建后，需要分别执行积分发放、消息通知和数据统计：

```text
OrderCreated
    ├─ PointsObserver
    ├─ NotificationObserver
    └─ AnalyticsObserver
```

增加一种后续处理时，只需注册新的观察者，不必修改订单创建的核心流程。这可以降低发布者与多个后续动作之间的直接耦合。

经典观察者模式通常发生在同一进程内，发布者直接持有并调用观察者；发布订阅模式通常引入事件总线或消息中间件，使发布者和订阅者不必直接认识。因此，消息队列可以实现类似的事件协作，但不等同于经典观察者模式。

使用观察者模式时还要考虑通知顺序、异常隔离、重复消费和订阅者注销。对于支付、扣款等关键流程，不能只“发出通知就不管”，还需要事务消息、重试或幂等机制保证结果可靠。

### 2.5 模式对比

| 模式 | 核心问题 | 变化点 |
| --- | --- | --- |
| 工厂 | 应该创建哪个对象 | 对象类型和构造过程 |
| 策略 | 应该执行哪种算法 | 业务规则和算法 |
| 单例 | 如何管理唯一共享实例 | 对象生命周期 |
| 观察者 | 状态变化后通知谁 | 事件订阅关系 |
