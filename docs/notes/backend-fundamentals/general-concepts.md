# 通用基础

## 1. 设计原则：SOLID

SOLID 是面向对象设计中五条常见原则的缩写。它们关注的不是把代码拆得越细越好，而是控制职责、依赖和变化的影响范围，使系统更容易理解、扩展和测试。

### 1.1 单一职责原则（SRP）

单一职责原则指一个类或模块应该只负责一类职责，最好只有一个引起它变化的原因。它的目的不是机械地把类拆得越小越好，而是降低修改的影响范围，提高代码的可维护性、可读性和可测试性。

例如在订单系统中，如果 `OrderService` 同时负责价格计算、库存扣减、订单创建、消息通知和报表统计，它就承担了过多职责。更合适的做法是把价格、库存和通知等逻辑交给独立组件，`OrderService` 只负责下单流程的编排。

### 1.2 开闭原则（OCP）

开闭原则指软件实体应该**对扩展开放，对修改关闭**。当系统增加一种新能力时，应该尽量通过新增实现来完成，而不是反复修改已经稳定的核心流程，从而减少回归风险。

例如支付系统支持支付宝和微信支付时，如果 `PaymentService` 使用一个不断增长的 `if-else` 判断支付类型，那么每增加一种支付方式都要修改它。更合适的做法是定义统一的 `PaymentMethod` 接口，每种支付方式提供自己的实现，核心流程只负责选择并调用对应实现。

### 1.3 里氏替换原则（LSP）

里氏替换原则指子类型必须能够替换父类型，并且不破坏调用方原有的正确性。子类型不仅要满足相同的方法签名，还要遵守父类型承诺的行为，例如输入约束、返回结果和异常语义。

例如系统定义了支持 `save` 和 `get` 的 `Storage`，本地存储和对象存储都应该能够正常实现这两个操作。如果某个只读存储继承 `Storage` 后，在调用 `save` 时直接抛出“不支持”异常，它就不能真正替换父类型。此时应拆分读写接口，而不是建立不恰当的继承关系。

### 1.4 接口隔离原则（ISP）

接口隔离原则指调用方不应该依赖自己不需要的方法。与其设计一个包含大量能力的通用接口，不如按照使用场景拆成多个小而明确的接口，避免一个无关方法的变化影响所有实现者。

例如一个 `UserService` 接口同时包含用户查询、修改、数据导出和邮件发送，仅读取用户信息的调用方也会被迫依赖后面三类能力。可以将它拆成 `UserReader`、`UserWriter`、`UserExporter` 等接口，让调用方只依赖实际使用的部分。

### 1.5 依赖倒置原则（DIP）

依赖倒置原则指高层业务逻辑不应该直接依赖具体的底层实现，高层和底层都应该依赖稳定的抽象。这样底层技术发生变化时，核心业务流程不需要随之修改，也更容易在测试中替换外部依赖。

例如 `OrderService` 如果直接创建某个支付 SDK 的客户端，业务逻辑就会与该供应商绑定。更合适的做法是让它依赖 `PaymentGateway` 接口，再由外部注入具体实现。切换支付供应商或编写单元测试时，只需替换实现，不必修改订单流程。

## 2. 常用设计模式

设计模式是对一类重复设计问题的通用解决方案。它描述对象应该如何分工与协作，而不是一段可以直接复制的固定代码。只有当相应的变化和复杂度真实存在时，使用设计模式才有价值。

### 2.1 工厂模式

工厂模式把**使用对象**与**创建对象**分开：调用方只表达自己需要什么，不直接决定具体类型如何构造。

例如支付系统同时支持支付宝和微信支付，可以让两种支付实现遵守同一个 `PaymentMethod` 接口，再由工厂根据支付类型返回对应实现：

```text
OrderService
    ↓ 请求 paymentType
PaymentFactory
    ├─ alipay → AlipayPayment
    └─ wechat → WechatPayment
```

这样 `OrderService` 不需要知道 SDK 客户端如何初始化，也不负责管理不同支付实现的构造参数。对象创建逻辑发生变化时，业务流程通常不需要修改。

工厂模式有几个常见层次：

- **简单工厂**：由一个工厂方法通过条件判断创建不同对象。实现简单，但新增类型仍要修改工厂；它不属于 GoF 23 种模式。
- **工厂方法**：为每类产品提供相应工厂，通过新增工厂和产品实现扩展。
- **抽象工厂**：负责创建一组相互关联的对象，例如同时创建某个云厂商的存储、消息和监控客户端。

如果对象构造非常简单、实现类型也不会变化，直接创建通常更清楚，不必为了模式额外增加工厂层。

### 2.2 策略模式

策略模式把一组可以互相替换的算法封装为独立实现，调用方通过统一接口使用它们。它解决的是**同一个业务目标存在多种实现方式**的问题。

例如电商系统可能同时存在普通会员、VIP 和促销活动三种计价规则：

```text
PriceService
    ↓ 使用 PricingStrategy
    ├─ NormalPricing
    ├─ VipPricing
    └─ PromotionPricing
```

`PriceService` 只负责调用当前策略，不需要在核心流程中维护不断增长的 `if-else`。具体策略可以由配置、用户类型或工厂在运行时选择。

策略模式与工厂模式经常配合使用，但两者目的不同：**工厂负责创建哪个对象，策略负责执行哪种行为**。如果算法只有一种且没有变化预期，引入策略接口只会增加不必要的间接层。

### 2.3 单例模式

单例模式保证一个类在特定作用域内只有一个实例，并提供统一的获取方式。它适合管理进程内需要共享且创建成本较高的对象，例如配置中心客户端、指标注册器或连接池管理器。

实现单例通常需要处理两个问题：

1. **唯一创建**：构造过程不能被调用方任意执行；
2. **并发安全**：多个线程同时首次访问时，不能创建多个实例。

常见实现包括启动时直接创建的饿汉式、首次使用时创建的懒汉式，以及双重检查锁。双重检查锁还必须依赖语言提供的内存可见性保证；例如 Java 通常需要配合 `volatile`，Go 通常使用 `sync.Once`。

单例也有明显边界：

- 单例对象的创建是线程安全的，不代表它内部的可变状态也是线程安全的；
- 进程内只有一个实例，不代表分布式系统中全局只有一个实例；
- 隐式全局状态会增加测试和并发推理难度，依赖注入容器管理的单例作用域通常更容易控制。

### 2.4 观察者模式

观察者模式在一个对象状态发生变化时，通知所有订阅者执行相应操作。发布者只维护统一的观察者接口，不需要了解每个订阅者的具体逻辑。

例如订单创建后，需要分别执行积分发放、消息通知和数据统计：

```text
OrderCreated
    ├─ PointsObserver
    ├─ NotificationObserver
    └─ AnalyticsObserver
```

增加一种后续处理时，只需注册新的观察者，不必修改订单创建的核心流程。这可以降低发布者与多个后续动作之间的直接耦合。

经典观察者模式通常发生在同一进程内，发布者直接持有并调用观察者；发布订阅模式通常引入事件总线或消息中间件，使发布者和订阅者不必直接认识。因此，消息队列可以实现类似的事件协作，但不等同于经典观察者模式。

使用观察者模式时还要考虑通知顺序、异常隔离、重复消费和订阅者注销。对于支付、扣款等关键流程，不能只“发出通知就不管”，还需要事务消息、重试或幂等机制保证结果可靠。

### 2.5 模式对比

| 模式 | 核心问题 | 变化点 |
| --- | --- | --- |
| 工厂 | 应该创建哪个对象 | 对象类型和构造过程 |
| 策略 | 应该执行哪种算法 | 业务规则和算法 |
| 单例 | 如何管理唯一共享实例 | 对象生命周期 |
| 观察者 | 状态变化后通知谁 | 事件订阅关系 |

## 3. 领域驱动设计（DDD）

领域驱动设计的本质是：**把软件设计的起点从“数据库表的增删改查”拉到“业务领域”，用统一的语言和模型来隐藏复杂业务的复杂性。**

简单系统直接面向数据库设计表就够了；一旦业务复杂，就必须先从业务本身思考。DDD 正是应对复杂业务的一套设计方法。它随微服务兴起而受重视，因为微服务最难的问题是“一个大系统按什么维度拆”，而 DDD 给出的答案是**按业务领域拆**，这恰好是它的强项。

理解整个 DDD 只需抓两条主线：**建立通用语言，再做模型驱动设计**。后面所有名词都挂在这两条主线上。

其中通用语言解决“说同一套话”，模型驱动设计解决“把话落进代码”。这里需要先说清模型指什么：**模型不是数据库表，也不是 UML 图，而是用通用语言把业务领域里的概念、规则、关系抽象出来、并能直接映射到代码的那套东西**，由实体、值对象、聚合、领域服务、领域事件等构件搭成。它的核心要求是：**业务概念、领域模型、代码三者是同一个东西的三种形态，必须严格一致。**

| | 传统数据库驱动 | 模型驱动设计 |
| --- | --- | --- |
| 设计起点 | 先设计表结构 | 先建领域模型 |
| “订单”是什么 | 一张 `order` 表加一堆字段 | 一个 `Order` 聚合根，带行为（下单、撤单）和规则 |
| 业务规则放哪 | 散落在 Service 的 if-else 里 | 封装在模型自身（实体、值对象、领域服务） |
| 谁驱动谁 | 表结构驱动代码 | 业务模型驱动代码 |

后续内容就是围绕这两条主线展开：先建立通用语言找到模型（3.1），再通过战略设计把模型分到不同限界上下文、战术设计决定每个上下文内部怎么组织模型（3.2、3.3）。

### 3.1 通用语言：让业务和开发说同一套话

通用语言指在业务人员和开发人员之间建立一套共有语言，让双方对“有哪些概念、哪些操作”达成一致。好的设计要贴近问题，而贴近问题的前提是双方不各说各话。

通用语言要说清业务里的概念和操作，例如电商里有“产品、订单”等概念，产品有“上架、下架”、订单有“下单、撤单”等操作。

建立通用语言的方法叫**事件风暴**，关注点是**领域事件**（记录业务中发生过的重要事情），分三步：

1. 找出领域事件：如“产品已上架”“订单已下单”；
2. 找出引发事件的动作：如“上架”“下单”；
3. 找出与事件、动作相关的实体或聚合：如“产品”“订单”。

关键是让不同角色一起参与，让知识在所有人脑中构建，得到大家都认同的结果。

### 3.2 战略设计：按业务领域拆系统

战略设计是高层设计，做两件事——先划分业务，再把业务落到代码组织上。

**划分业务：子域。** 领域对应“要解决的问题”，分而治之就是把大领域拆成小的子域，拆的关键是找出不同的关注点（同一个“用户”，在身份管理里是“用户”，在项目管理里是“项目成员”）。子域按重要性分三类：

| 子域类型 | 含义 | 投入策略 |
| --- | --- | --- |
| 核心域 | 系统最重要的部分，业务成功的关键 | 全力投入 |
| 支撑域 | 不是核心竞争力，但系统不得不做（如排行榜） | 次要投入 |
| 通用域 | 行业通用做法，不自己做也不影响业务（如发通知） | 甚至可以买服务 |

**落地业务：限界上下文。** 限界上下文的本质是一个限定了通用语言生效范围的边界，出了界含义就不保证了。同样说“订单”，交易上下文和物流上下文的订单是不同的。它最重要的特性是**完全独立**，因此可以看作一个独立系统、对应一个微服务，从而避免“完成一个业务功能要跑到一堆其他服务里做事”这个微服务最容易出问题的点。

上下文之间要交互，把交互方式画出来就是**上下文映射图**；最典型的一种交互是**防腐层**——在外部模型和内部模型之间建一个翻译层，把外部模型转成内部模型，防止外部概念污染自己。

子域与限界上下文容易混淆，重点区分：

| 维度 | 子域 | 限界上下文 |
| --- | --- | --- |
| 关注点 | 我要解决**什么问题**（业务功能、逻辑） | 我**怎么解决**这个问题（实现模型） |
| 角色 | 划定业务领域内一块特定区域 | 为该区域提供一致的模型或解决方案 |

两者不一定一一对应：一个限界上下文可含多个子域，一个子域也可横跨多个限界上下文。

### 3.3 战术设计：组织业务模型

战术设计是低层设计，本质是在领域问题这个“故事背景”下，找出角色、理清关系、让它们互动起来。

**角色：实体与值对象。**

| 类型 | 本质 | 判断相等 | 例子 |
| --- | --- | --- | --- |
| 实体 | 有**唯一标识符**，标识不变就还是它 | 比标识符 | 订单（靠订单号，状态变了还是同一个订单） |
| 值对象 | 只表示一个**值**，无标识符 | 比所有属性 | 订单地址（省市区加住址） |

很多值对象没被识别出来：用字符串存电话、用 double 存价格都不合适。价格有精度限制和计算规则，应该封装成一个值对象类。

**关系：聚合与聚合根。** 把多个实体或值对象组合成同生共死的整体就是聚合（订单作废，订单项也没用了）。聚合像一棵树，树根是聚合根，它是从外部访问聚合的唯一起点——要访问订单和订单项，必须先通过订单号找到订单，再把订单项一并取出。

**互动：领域服务、工厂、仓库、应用服务。**

- 领域服务：承载那些不自然属于任何单个实体的动作（如“转账”牵扯两个账户，不该放进某一个账户实体），操作对象是聚合根。
- 工厂：一类特殊动作——创建对象。聚合根由工厂创建，聚合内的子对象则要从聚合根创建（订单项应由订单上的工厂方法产生），以保证关联关系。
- 仓库（Repository）：把领域对象的变更结果保存下来，可简单理解为持久化。
- 应用服务：领域服务搭好、核心逻辑成型后，需要一个协调者串起完整业务流程，这就是应用服务。

领域服务与应用服务的区别：

| 维度 | 领域服务 | 应用服务 |
| --- | --- | --- |
| 出发点 | 业务逻辑本身 | 业务用例流程 |
| 职责 | 处理领域内部、不属于某实体的逻辑（如“加入购物车”） | 协调多个领域对象或领域服务完成一个用例（如“支付”要串起库存、订单、支付） |
| 一句话 | 实现业务规则 | 实现用例流程，整合多个领域服务 |

### 3.4 实践落地顺序

一个电商系统的典型落地步骤：事件风暴识别关键领域事件 → 领域建模识别聚合根（用户、商品、购物车、订单）及其关系 → 确定子域和限界上下文并保证每个上下文内模型含义一致 → 定义领域服务处理不属于任何实体的逻辑 → 设计应用服务执行业务流程 → 用领域命令和领域事件驱动流程 → 为每个聚合根设计仓储做持久化。

命令与事件的区别是高频区分点：

| 维度 | 命令（Command） | 事件（Event） |
| --- | --- | --- |
| 语义 | **要做**某事（指令性） | **已经做了**某事（过去的事实） |
| 时态 | 将来、正在要做 | 过去已发生 |
| 接收者 | 明确的一个 | 零个、一个或多个 |
| 同步性 | 期望接收者执行 | 异步、非阻塞 |
| 例子 | “创建订单”“提交支付” | “订单已创建”“支付已成功” |

一句话：命令是“去做某事”，事件是“已经做了某事”。

### 3.5 关键忠告

不要为了微服务而微服务。一次性把边界划清楚很难，所以先按划出的限界上下文在一个进程里分模块（进程内调整成本低），让各上下文独立演化，等某个上下文演化到“值得独立部署”时，再考虑真正拆成微服务。

### 面试问答

**Q：DDD 是什么？它和微服务是什么关系？**

DDD 是一套应对复杂业务的设计方法，核心是把设计起点从数据库表拉到业务领域，用通用语言和领域模型隐藏业务复杂度。整个方法就两条主线：先和业务方一起用事件风暴建立通用语言，再做模型驱动设计——战略设计按业务领域把系统拆成子域、落到限界上下文，战术设计再用实体、值对象、聚合、领域服务、应用服务把模型组织起来。

它和微服务的关系是：微服务最难的是“怎么拆”，而 DDD 的限界上下文天然对应一个可独立部署的微服务边界，所以它给了拆分微服务的业务视角。但要先在进程内分模块、独立演化，等值得独立部署时再拆，不要为了微服务而微服务。
