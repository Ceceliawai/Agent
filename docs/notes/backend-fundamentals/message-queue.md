# 消息队列

消息队列的核心链路是：**生产者发送消息，Broker 接收并保存消息，消费者获取并处理消息，处理成功后提交消费确认。**

消息队列主要解决解耦、异步和削峰问题，但同时会引入消息丢失、重复消费、顺序错乱、消息积压和最终一致性等问题。因此，学习消息队列不能只关注“如何发送消息”，而要沿着消息的完整生命周期分析每个阶段可能发生的故障。

生产者需要处理消息发送失败，Broker 需要通过持久化和副本机制保存消息，消费者需要在业务处理成功后确认消息，并通过幂等机制应对重复投递。消息积压超过系统处理能力时，还需要扩容、限流或快速失败，消息队列不能无限吸收流量。

## 1. 消息队列的基本概念与作用

### 1.1 基本角色

消息队列包含生产者、Broker 和消费者三个基本角色：

| 角色 | 主要职责 | 需要关注的问题 | 订单场景示例 |
| --- | --- | --- | --- |
| 生产者（Producer） | 创建消息并发送给 Broker | 发送确认、失败重试、业务唯一键 | 订单服务发送“订单已创建”消息 |
| Broker | 接收、存储并投递消息 | 持久化、副本、路由、消息积压 | 保存订单消息并投递给下游 |
| 消费者（Consumer） | 获取消息并执行业务逻辑 | 消费确认、失败重试、幂等 | 积分服务收到消息后增加积分 |

三者构成的完整链路是：**生产者发送消息 → Broker 存储和投递消息 → 消费者处理并确认消息。**

Topic、队列或分区、消费者组是组织和分发消息的概念，不属于三个核心角色。

消息队列主要解决解耦、异步和削峰三个问题。三者关注的对象不同：

| 作用 | 改变的对象 | 核心价值 |
| --- | --- | --- |
| 解耦 | 系统依赖关系 | 上下游可以独立演进 |
| 异步 | 任务执行时间 | 缩短主链路响应时间 |
| 削峰 | 流量的时间分布 | 避免瞬时流量压垮下游 |

### 1.2 解耦

没有消息队列时，订单服务需要直接调用积分、优惠券、短信等下游服务。新增下游需要修改订单服务，某个下游发生故障也可能拖慢整个下单流程。

引入消息队列后，订单服务只负责发布“订单已创建”事件。各个下游服务根据需要订阅消息，不需要与订单服务直接耦合。

解耦的本质是：**生产者从依赖具体的下游服务，变成依赖稳定的业务事件。**

### 1.3 异步

下单过程中，创建订单、校验库存等核心操作通常需要同步完成；增加积分、发放优惠券和发送通知等操作不一定需要用户等待。

生产者可以在核心操作完成后发送消息并返回结果，其余任务由消费者在后台处理，从而缩短同步调用链路和接口响应时间。

异步的本质是：**将不需要立即完成的操作移出同步调用链路。**

必须立即获得处理结果的操作不适合简单地改为异步。例如，调用方必须马上知道支付是否成功时，不能只发送一条消息便直接返回支付成功。

### 1.4 削峰

假设秒杀系统瞬间收到每秒 10 万个请求，但数据库每秒只能处理 1 万个请求。所有请求直接访问数据库时，瞬时流量可能耗尽数据库连接、CPU 等资源。

引入消息队列后，请求先进入队列，消费者再按照数据库能够承受的速度处理。突发流量被转换成一段时间内相对平稳的流量。

削峰的本质是：**用排队时间换取下游系统的稳定性。**

消息队列只能缓冲短期流量。如果生产速度长期大于消费速度，消息仍会持续积压，最终必须扩容、限流或快速失败。

### 1.5 引入成本

消息队列不会消除系统复杂度，而是把同步调用问题转换成异步系统问题。系统需要额外处理：

- 消息丢失
- 重复消费
- 消息乱序
- 消息积压
- 最终一致性
- 监控、重试、对账和补偿

同一消费者组内的消费者共同分担消息，不同消费者组可以各自消费一份。同组有效并发通常受队列或分区数量限制，消费者数量更多不代表吞吐量一定更高。

### 面试问答

**Q1：为什么要使用消息队列？**

消息队列主要用于解耦、异步和削峰。解耦是让上游只发布业务事件，不直接依赖所有下游；异步是把积分、通知等非核心操作移出同步调用链路；削峰是让突发请求先进入队列，下游按照自身处理能力消费。但消息队列也会引入消息丢失、重复消费、乱序、积压和最终一致性等问题，因此业务简单或必须同步获得结果时，没有必要使用消息队列。

## 2. 消息可靠性：怎样保证不丢

消息可靠性需要覆盖生产者、Broker 和消费者三段链路。生产者负责确保消息进入 Broker，Broker 负责可靠保存消息，消费者负责确保消息对应的业务真正执行成功。

### 2.1 生产者可靠性

生产者的目标是确保消息成功进入 Broker，具体流程如下：

1. 为消息生成稳定的业务唯一标识。
2. 将消息发送给 Broker。
3. 等待 Broker 返回生产确认。
4. 收到确认后，认为消息已经被 Broker 接收。
5. 发送失败或等待确认超时，使用相同的业务标识重试。
6. 超过重试次数后，记录失败状态并触发告警。
7. 关键消息可以先落库，再由后台任务扫描并补发。

生产者没有收到确认时，无法判断 Broker 是没有收到消息，还是已经保存消息但确认丢失。为了避免消息丢失，生产者只能重新发送，因此可能产生重复消息。

不同中间件提供了不同的生产确认机制。例如，RabbitMQ 使用 Publisher Confirm；Kafka 通过 `acks` 参数控制 Broker 在什么条件下返回确认。

生产者收到 Broker 的确认，只能证明消息已经进入消息队列，不能证明消费者已经完成业务处理。

### 2.2 Broker 可靠性

Broker 的目标是确保已经接收的消息不会因为节点故障而丢失，主要通过以下方式实现：

1. 将消息写入持久化存储，避免进程或机器重启后消息消失。
2. 将消息复制到其他副本，避免单个节点或磁盘故障造成数据丢失。
3. 达到配置的持久化和副本条件后，再向生产者返回确认。
4. 当前节点故障时，由其他副本继续保存或提供消息。

以 Kafka 为例，不同的 `acks` 配置代表不同的确认条件：

| `acks` 配置 | 确认时机 | 可靠性 |
| --- | --- | --- |
| `acks=0` | 生产者不等待 Broker 确认 | 最低 |
| `acks=1` | 分区主副本接收消息后确认 | 主副本故障时仍可能丢失 |
| `acks=all` | 当前同步副本集合达到要求后确认 | 更高 |

`acks=all` 通常需要配合 `min.insync.replicas`。当同步副本数量低于最小要求时，Broker 拒绝写入，而不是在副本不足的情况下继续返回成功。

确认条件越严格，消息可靠性越高，但写入延迟和暂时无法写入的概率也会提高。

### 2.3 消费者可靠性

消费者的目标是确保消息对应的业务真正执行成功，正确的处理顺序如下：

1. 从 Broker 获取消息。
2. 根据业务唯一标识检查消息是否已经处理。
3. 执行业务操作。
4. 提交数据库事务。
5. 向 Broker 发送消费确认，或者提交消费位置。

消费者不能先确认消息再处理业务。否则 Broker 会先将消息标记为已消费；消费者随后处理业务时一旦宕机，Broker 不会再次投递，消息对应的业务就会丢失。

如果消费者已经提交数据库事务，但在发送消费确认之前宕机，消息会被重新投递或重新读取。此时业务没有丢失，但可能被重复执行，因此消费者必须实现幂等。

不同中间件的消费确认方式不同。RabbitMQ 由消费者发送 Consumer Acknowledgement；Kafka 通常在业务处理成功后提交消费位置；RocketMQ 由消费者返回消费成功状态。

### 2.4 端到端可靠性

| 组件 | 可靠性职责 |
| --- | --- |
| 生产者 | 等待 Broker 确认，发送失败时重试，关键消息落库补发 |
| Broker | 持久化消息，通过副本避免单点故障导致消息丢失 |
| 消费者 | 业务成功后再确认，通过幂等处理重复消息 |

生产确认、Broker 持久化和消费确认缺一不可。可靠消息通常采用“至少一次投递 + 消费者幂等”，并通过监控、对账和补偿处理极端异常。

### 面试问答

**Q1：如何保证消息不丢失？**

按照生产者、Broker 和消费者三段回答。生产者等待 Broker 返回确认，发送失败时重试，关键消息可以落库补发；Broker 开启持久化和副本复制，达到可靠性条件后再返回确认；消费者在业务处理成功并提交数据库事务后再确认消息。最后还要通过监控、对账和补偿处理极端异常。

**Q2：至少一次和恰好一次有什么区别？**

至少一次强调消息不能漏，发生超时或故障时通过重试保证消息最终到达，代价是消息可能重复。恰好一次强调同一业务效果只能出现一次，不仅要求消息系统控制重复，还需要数据库和外部系统共同保证。Kafka 事务可以覆盖 Kafka 内部的读取、处理和写回，但如果消费者还要修改数据库或调用外部接口，仍然需要业务幂等或其他事务机制。

## 3. 重复消费与幂等

消息中间件在工程上通常只能保证至少一次投递，因此重复消费是必然会出现的情况，而不是异常。要获得恰好一次的业务效果，无法仅依靠开启某个参数实现，正确性最终要由消费端的幂等设计保证。

重复消费的根本原因是：**业务处理和消费确认无法合并成一个原子操作。** 只要两者之间存在失败窗口，消息就可能被重复投递。

### 3.1 重复消费的来源

重复来自生产端和消费端两侧，本质都是“操作已执行，但结果无法被确认”：

- 生产者发送超时后重试。生产者无法判断消息是没有写入 Broker，还是已经写入但确认丢失，为避免丢失只能重发，因此产生重复。
- 消费者完成业务但确认失败。消费者已经执行业务（例如账单已更新），但在返回消费确认前宕机或网络中断，Broker 看不到成功结果，会将消息重新投递。
- 消费者宕机或发生重新分配后，从上一次提交的位置继续消费。已处理但尚未提交位置的消息会被重新读取。

### 3.2 幂等的含义

幂等的本质是：**同一业务消息执行一次或多次，最终业务结果保持一致。** 幂等约束的是最终结果，而不是“只执行一次”。据此可以判断某个消费逻辑是否需要额外设计：

| 操作类型 | 示例 | 是否需要额外控制 |
| --- | --- | --- |
| 查询、覆盖写 | 将状态设置为某个确定值 | 天然幂等，重复执行不改变结果 |
| 带增量副作用的操作 | 扣库存、转账、发券 | 需要额外控制，重复执行会累加 |

### 3.3 业务唯一键

去重需要一个稳定、唯一、由业务定义的标识，优先使用订单号、支付单号、流水号等业务标识。

不能只依赖消息系统生成的消息 ID。生产者超时重发时，同一笔业务可能被赋予不同的消息 ID，用它去重会把两条本质相同的消息判定为不同消息而全部放行。业务唯一键之所以可靠，是因为它标识的是业务本身，而不是某一次传输。

### 3.4 常见幂等方案

不同方案解决的问题不同，通常需要按“防并发”和“防重复”两个层面组合使用：

| 方案 | 方案说明 | 解决的问题 | 注意点 |
| --- | --- | --- | --- |
| 数据库唯一约束、去重表 | 为业务唯一键建立唯一索引或单独的去重表，处理业务前先尝试插入一条去重记录 | 通过主键或唯一索引冲突挡住重复插入 | 必须与业务修改处于同一事务 |
| 业务状态机 | 为业务实体定义合法状态及流转，消费时先校验当前状态，只有处于允许状态才执行并推进到下一状态 | 未处理才处理，并推进状态 | 天然应对重复，且可读、可审计 |
| 带版本条件的更新（乐观锁） | 更新时在条件中带上期望的状态或版本号，如 `update ... where status=? / version=?`，条件不匹配则不生效 | 保证同一业务修改只生效一次 | 适合覆盖写 |
| Redis `SET NX` | 以业务唯一键为 key 尝试写入，只有第一个写入成功的消费者继续处理，其余被拦截 | 拦截并发重复 | 不能单独使用，需处理锁过期，且无法证明数据库业务已经成功 |

其中 `SET NX` 拦截的是同一时刻的并发重复，而唯一约束和状态机保证的是跨时间的最终一致。前者关注并发，后者关注正确性，转账、库存等操作还需配合流水记录和状态机。

### 3.5 原子性要求

去重记录与业务修改必须处于同一个数据库事务中，要么一起成功，要么一起回滚。

常见的错误做法是先写入“已消费”标记，再执行业务。一旦业务失败，重试时会读到“已消费”而直接跳过，业务永远无法完成，却被系统认为已完成。正确的顺序是：**在同一个事务内完成去重判断和业务修改，事务提交成功后再发送消费确认。**

### 面试问答

**Q1：消息为什么会被重复消费？**

根本原因是消费确认和业务处理不是一个原子动作。消费者可能已经写库成功，但在返回确认前宕机，Broker 看不到成功结果就会重新投递；生产者发送超时也会重发同一笔业务消息。只要系统选择至少一次投递，就必须接受重复的可能，并把正确性交给消费端幂等保证。

以支付为例，消费者更新账单后、发送确认前网络中断，Broker 会把消息交给另一个消费者。若消费逻辑是“余额减一百”，第二次就会多扣一次；若逻辑是“支付单未处理才扣款，并将状态改为已处理”，重复消息只会读到已处理状态并退出。

**Q2：消费者如何保证幂等？**

先选择稳定的业务唯一键，再让去重判断和业务修改处于同一原子边界。常用做法是数据库唯一索引、去重表，或用订单状态和版本号做条件更新；`SET NX` 适合拦截并发，但不能单独证明数据库业务已经成功。转账、库存等操作还需配合流水和状态机。

以订单号建立唯一约束为例，两个消费者同时处理同一订单时，只有一个能插入成功，另一个遇到主键冲突后跳过。但若去重表和业务表分两次提交，第一步成功、第二步失败，重试就会把未完成的业务当成已完成，因此必须把两张表的修改放进同一事务。

## 4. 顺序消息

严格的全局有序要求所有消息进入同一条队列、由单个消费者串行处理，吞吐量受限，生产系统很少采用。实际工程中保证的是局部有序，即只让同一业务实体（同一订单、同一用户、同一设备）的消息有序，不同实体之间仍然并行。

保证顺序需要三层配合，缺一层都可能出现状态倒退：**固定路由解决存储顺序，串行消费解决处理顺序，业务状态机负责最终校验。**

### 4.1 全局有序与局部有序

| 类型 | 含义 | 代价 | 适用性 |
| --- | --- | --- | --- |
| 全局有序 | 所有消息严格按发送顺序处理 | 只能单队列、单消费者串行，吞吐量受限 | 极少使用 |
| 局部有序 | 仅同一业务键的消息有序 | 不同业务键可并行，吞吐量不受影响 | 生产系统的通用选择 |

顺序的粒度应当由业务定义。绝大多数场景只需要“同一订单、用户或设备内有序”，把粒度定得过粗（趋近全局有序）会白白牺牲并发能力。

### 4.2 固定路由

生产者用订单号、用户 ID 等业务键选择目标队列或分区，使同一业务实体的消息始终进入同一条有序日志，不同业务键的消息仍可分散到不同队列并行处理。

固定路由解决的是存储顺序。只有先保证同一实体的消息落在同一条队列中，后续的串行消费才有意义。如果同一订单的创建、支付、发货被分到不同分区，多个消费者可能先处理发货，顺序在存储阶段就已经被打乱。

### 4.3 串行消费

同一队列或分区内按顺序处理，前一条消息未完成时不能让后一条越过。

串行消费解决的是处理顺序。需要提高并发时，应当增加业务分组（即增加队列或分区数量），而不是拆散同一组消息让多个消费者并行处理同一条队列，后者会直接破坏顺序。因此顺序消息的并发上限，取决于业务键能划分出多少个互不影响的分组。

### 4.4 失败处理与状态机校验

串行消费带来一个新问题：某条消息处理失败时，后续消息不能直接越过它，否则顺序被破坏；但无限重试又会长期阻塞整条队列。

- 失败处理：设置重试上限，超过后将消息转移到异常队列并转人工处理，避免单条消息长期卡住后续消息。
- 状态机校验：业务层用状态机校验状态跳转，拒绝“已退款又回到已支付”这类非法跳转。

状态机是顺序保证的最后一层。即使前两层已经就位，重放和补偿仍可能造成乱序，只有在业务层校验状态跳转是否合法，才能防止状态倒退。

### 面试问答

**Q1：如何保证消息顺序消费？**

通常保证局部有序，通过三层配合实现：生产端把同一订单号或用户 ID 的消息路由到同一个队列或分区；消费端对这条队列串行处理，某条消息失败时后续消息不能越过它，需要重试或转入异常队列；业务层再用状态机校验状态跳转，防止重放和补偿造成乱序。

以订单为例，依次产生创建、支付、发货三条消息。如果它们被分到不同分区，三个消费者可能先处理发货；即使在同一分区，支付失败后直接跳过也会让发货先落库。固定业务键解决存储顺序，串行消费解决处理顺序，状态机负责最后校验，三层少一层都可能出现状态倒退。

## 5. 消息积压与消费排查

消息积压的本质是：**生产速率持续大于消费速率，差值随时间累积。** 处理积压不是简单地“多开消费者”，而是要先定位瓶颈，再从“可并行单元、消费能力、下游容量”三个方向同时调整，并评估追平所需的时间。

排查时的第一原则是先定位、后扩容。在没有找到瓶颈之前盲目加机器，往往无效甚至有害。

### 5.1 核心指标

只看队列长度无法判断问题正在扩大还是已经恢复，需要同时观察多项指标：

| 指标 | 作用 |
| --- | --- |
| 生产速率、消费速率 | 比较两者差值，判断积压在扩大还是在收敛 |
| 积压量 | 反映当前堆积的总量 |
| 最老消息延迟 | 反映最早的未处理消息已等待多久 |
| 失败率 | 判断消费变慢是否由错误重试导致 |
| 单条处理耗时 | 定位单条消息在哪个阶段变慢 |

关键在于比较生产速率与消费速率：只要消费速率低于生产速率，积压就会持续增加；只有消费速率反超，积压才开始收敛。

### 5.2 排查方向

消费变慢可能出现在链路的任意一环，需要分层排查：

- 生产侧：生产流量突增。
- 消费者自身：实例异常、重平衡、线程池耗尽。
- 依赖的下游：数据库慢 SQL、锁等待、连接池耗尽、下游 RPC 超时。
- 基础设施：Broker 磁盘、网络或副本状态异常。

一个容易误判的现象是：消费者 CPU 很低不代表它没问题，它可能全部阻塞在数据库连接池或下游超时上，此时增加线程只会堆积更多等待请求。有效的做法是把单条消费拆成拉取、反序列化、业务计算、数据库、RPC、确认几个阶段分别计时，从而判断瓶颈在消费者内部还是在它依赖的系统。

### 5.3 并发上限

同一消费者组内，队列或分区是并行分配的基本单位。消费者数量超过队列或分区数量后，多出的实例通常拿不到任务。

因此提高消费并发不能只增加消费者实例，还必须增加队列或分区数量。这也是处理积压时“只多开消费者、分区数不变”往往无效的原因，多出的实例分不到分区，消费能力并未真正提升。

### 5.4 临时止血与大规模分流

定位到瓶颈后，可按积压规模选择手段：

- 临时止血：先恢复故障消费者，再按下游承载能力增加队列、消费者或处理线程；可批量写库的业务用批处理减少网络往返。
- 大规模分流：积压很大时，用临时消费者把原消息转发到更多临时队列，再由扩容后的消费者并行清理。分流过程必须保留消息键和去重信息，否则会破坏顺序和幂等。

### 5.5 恢复阶段的风险

清理积压时，追赶速度过快可能压垮数据库和下游，出现“刚清空队列又把下游打挂”的连锁故障。扩容必须以数据库和下游的容量为上限。

此外，分流和重试会引入重复和乱序，因此恢复阶段仍需依赖限流、幂等、状态校验和对账来保证正确性。

### 面试问答

**Q1：几百万条消息积压了怎么处理？**

我会分三步：先定位，再扩容，最后控制恢复风险。

第一步，先判断是生产突增还是消费故障。恢复消费者之后，对比生产速率和消费速率——只要消费追不上生产，积压就会一直涨。

第二步是扩容，但关键点是：扩容不等于多开消费者。因为分区或队列才是并发的基本单位，分区数不变时，多出来的消费者拿不到任务。所以要同时增加分区数、消费者数和处理线程，能批量写库的就改批处理。如果积压特别大，就先用一个临时消费者把消息转发到更多临时队列，再由扩容后的消费者并行清理，转发时要保留消息键和去重信息。

第三步，扩容要看数据库和下游的容量，不能刚清空队列又把下游打挂；而且分流和重试会带来重复和乱序，得靠幂等和状态校验兜底。最后我会按当前消费能力估算一下大概多久能追平。

**Q2：消费速度突然下降怎么排查？**

我的原则是先定位再扩容，定位之前不盲目加机器。

第一步先看监控：积压曲线加上生产、消费速率，确认是从哪个时间点开始下降的，先把范围圈出来。

第二步分两个方向查。消费者这一侧，看实例是否存活、有没有重平衡、线程池和失败重试是否正常；依赖这一侧，重点看数据库慢 SQL、锁等待、连接池，以及下游 RPC 超时。

这里有个容易踩的点：消费者 CPU 低不代表它没问题，它可能全部阻塞在数据库连接池或下游超时上，这时候加线程只会堆更多等待请求。所以我会把单条消费拆成拉取、反序列化、业务计算、数据库、RPC、确认几段分别计时，很快就能判断瓶颈是在消费者内部，还是在它依赖的下游。

## 6. 消费失败：重试、死信与延迟

消费失败处理的本质是：**先区分临时异常和永久业务错误，再用相反的策略应对。** 临时异常靠重试恢复，永久错误靠死信兜底，两者绝不能混在一起，否则重试队列会被永远不可能成功的消息占满。

### 6.1 异常分类

分类是整章的地基，决定一条失败消息该走哪条路：

| 类型 | 典型场景 | 能否靠重试恢复 |
| --- | --- | --- |
| 临时异常 | 网络抖动、限流、下游临时不可用 | 可以，稍后重试大概率成功 |
| 永久业务错误 | 参数错误、数据缺失、业务状态冲突 | 不能，重复执行结果不会变对 |

判断标准很直接：重复执行同样的操作，结果会不会改变。库存服务短暂超时，隔几秒再试可能成功；订单号不存在，重试一百次也不会变对。

### 6.2 退避与重试上限

对临时异常也不能立即无限重试，否则会持续冲击本就故障的下游，形成二次打击。需要三个限制：

- 重试间隔：按递增间隔（退避）重试，给下游恢复时间。
- 最大次数：超过上限就不再重试，转入死信。
- 重试流量限制：给重试单独限流，避免重试流量挤占正常消费。

### 6.3 死信队列

超过重试上限的消息转入死信队列，它的作用是隔离故障、保留现场、提供可审计的修复入口。死信记录应包含：

- 消息体、业务键
- 失败原因
- 重试次数

修复问题后，由受控任务（人工或定时）重放。关键点：重放不是简单地重新执行，消费者必须幂等，且重放前要重新检查业务状态，仍走原来的幂等校验。

### 6.4 毒消息隔离

毒消息指一条固定失败的消息。它的危害是长期堵住正常队列，让后面的正常消息也无法处理。

难点在顺序业务：普通队列可以直接把毒消息挪走，但顺序队列一旦跳过就破坏了顺序。因此顺序场景要在“保持顺序”和“跳过异常”之间按业务风险取舍，能容忍乱序就跳过，不能容忍就宁可阻塞并告警人工介入。

### 6.5 延迟执行

订单超时关闭、延迟通知、失败补偿等场景可以用延迟消息，让消息到期后再触发。

延迟消息的本质是：**消息先落到 Broker，但在到期前对消费者不可见，到点后才投递。** 常见实现有三类：

| 实现方式 | 代表中间件 | 机制 | 局限 |
| --- | --- | --- | --- |
| TTL + 死信队列 | RabbitMQ | 消息先发到只用于延迟的中转队列（不挂消费者、设 TTL），到期变成死信后经死信交换机转发到有消费者的业务队列被消费 | 队头检查过期，先进的长延迟消息会堵住后进的短延迟消息，不支持任意乱序到期 |
| 分级延迟 | RocketMQ | 生产时指定预设延迟等级，Broker 先写入内部延迟主题，到点再投递到真正的 Topic | 只能选等级，不能精确到任意时间（5.x 已支持任意定时消息） |
| 时间轮 / 定时投递 | 通用（Kafka 需自实现） | 消息带投递时间戳进入独立延迟存储，用时间轮或按时间排序结构管理，到点转移到正常队列 | 需要额外的调度与存储；Kafka 原生不支持，通常外挂 |

无论哪种实现，本质都是“先存下、到点才可见”。这里补充两种常见做法的实现要点：

RabbitMQ 延迟交换机插件（`rabbitmq_delayed_message_exchange`，现在的推荐方案）：

- 声明 `x-delayed-message` 交换机，发消息时用消息头 `x-delay` 指定延迟时间。
- 交换机收到后不立即路由，把消息存入 RabbitMQ 自带的 Mnesia 数据库。
- 用 Erlang 定时器为消息排定投递时间，到点后按正常路由规则投递到业务队列。
- 代价：延迟消息只存在声明交换机的节点上，高可用弱，消息量大时有丢失和性能压力。

时间轮（Kafka、Netty 等采用）：

- 一个环形数组，每个格子对应一个时间刻度，挂着到期时间落在该刻度的任务链表。
- 指针按固定间隔向前推进，走到哪个格子就触发该格子里到期的任务。
- 延迟超过一圈的任务放到更高层级的时间轮，逐层降级，避免数组过大。
- 优点：新增和触发都是 O(1)，适合海量定时任务。

这里还有一个必须记住的坑：**消息到期后不能直接执行旧指令，要先查询当前业务状态。** 延迟消息携带的是“过去某一刻的意图”，例如一条“订单超时关闭”的延迟消息到期时，订单可能已经支付，此时不能因为旧消息到达就把已支付订单关掉。

### 面试问答

**Q1：消费失败后，重试和死信怎么设计？**

我会先分类，再分别设计重试和死信，最后强调兜底。

第一步，先区分临时异常和永久业务错误。判断标准是重复执行结果会不会变——网络超时、限流是临时的，重试可能成功；参数错误、订单号不存在是永久的，重试多少次都没用。这两类一定要分开，否则重试队列会被无效消息占满。

第二步，临时异常按递增间隔重试，并限制最大次数和重试流量，避免一直冲击故障下游。

第三步，超过重试上限的消息进死信队列，保存消息体、业务键、失败原因和重试次数，把故障隔离、现场保留下来，等修复后由人工或定时任务重放。

最后要补一句兜底：消费者本身必须幂等，重放前还要重新校验业务状态；如果是订单超时这类延迟消息，到期后也不能直接执行旧指令，要先看当前状态。

## 7. 事务消息与最终一致性

事务消息要解决的本质是：**数据库事务和 MQ 属于两个系统，无法合并成一个事务。** 任何“先做一个、再做另一个”的写法都存在一个宕机窗口。解决思路是先把消息可靠地记录下来，再保证它迟早被发出去，最终达到一致。

### 7.1 双写问题

先更新数据库再发消息、和先发消息再更新数据库，都有各自的故障窗口：

| 顺序 | 故障场景 | 后果 |
| --- | --- | --- |
| 先提交数据库，再发消息 | 两步之间宕机，消息没发出 | 下游永远不知道订单已创建，漏通知 |
| 先发消息，再提交数据库 | 数据库回滚，消息已发出 | 下游处理一条并不存在的业务数据，如给回滚的订单发券 |

### 7.2 本地消息表（Transactional Outbox）

把“发消息”这件事也变成一次数据库写入，从而和业务数据共享同一个事务：

- 业务数据和待发送事件写入**同一个数据库事务**，一起提交或一起回滚。
- 后台任务或 CDC 扫描未发送的事件记录，投递到 MQ，失败就重试。
- Outbox 表保存事件 ID、聚合键、事件类型和内容：事件 ID 用于去重，聚合键用于保持同一实体的顺序。
- 发送状态更新失败可能造成重复投递，所以消费者仍必须幂等。

核心一句话：消息只要和业务数据一起提交进了数据库，就不会丢；发送失败也没关系，后台任务会一直重试直到发出去。

### 7.3 RocketMQ 事务消息

用“半消息 + 事务回查”两个机制，分别堵住双写的两个故障窗口：

1. 生产者先发送**半消息**，Broker 保存但**对消费者不可见**。
2. 生产者执行本地事务，然后向 Broker 返回提交或回滚。
3. 提交后消息才对消费者可见，回滚则删除或终止投递。
4. 如果第二次确认丢失（结果未知），Broker 会**回查**生产者的本地事务状态，再决定提交还是回滚。这里 Broker 无法直接看到确认是否丢失，而是靠**超时**判断：超过一定时间还没收到提交或回滚，就认为结果未知，主动发起回查，并且会定时多次回查。

两个机制各自解决一个问题：

- **半消息**：解决“本地事务完成后应用突然宕机，消息没有任何记录”。
- **事务回查**：解决“本地事务已完成，但提交结果没送到 Broker”。

关键点：回查依据必须来自**可查询的本地业务状态**（如查数据库订单状态），不能只看进程内变量，否则应用重启后就查不到了。

### 7.4 最终兜底

事务消息和本地消息表都只是**缩小了故障窗口**，并没有消灭重复和异常。下游仍可能重复收到消息，因此：

- 消费者幂等不能省。
- 还要配合业务对账和补偿任务，处理极端异常。

### 面试问答

**Q1：如何保证数据库操作和发消息的一致性？**

我会用本地消息表，也叫 Transactional Outbox，思路是把“发消息”也变成一次数据库写入。

第一步，先说清为什么难：数据库和 MQ 是两个系统，先写库再发消息，中间宕机就会漏发；先发消息再写库，库要是回滚了，下游就会处理一条不存在的数据。

第二步，做法是把业务数据和待发送事件放在**同一个数据库事务**里一起提交，保证要么都成功要么都失败。

第三步，再由后台任务或 CDC 扫描这张事件表，把消息投递到 MQ，失败就重试。

最后兜底：事件带唯一 ID、消费者做幂等，再配合对账补偿。本质是只要消息和业务数据一起落了库，就能靠重试保证迟早发出去。

**Q2：RocketMQ 事务消息怎么实现？**

它靠半消息和事务回查两步。

第一步，生产者先发一条**半消息**，Broker 存下来但暂不对消费者投递。

第二步，生产者执行本地事务，再告诉 Broker 提交还是回滚：提交了消息才对消费者可见，回滚就把它删掉。

第三步，如果这个提交或回滚的结果丢了，Broker 会**回查**生产者的本地事务状态，再决定投还是不投。这里 Broker 是靠超时发现自己一直没收到确认，才主动发起回查的。

补一句关键的：回查依据必须来自可查询的业务状态，比如查数据库里订单到底成没成，不能靠进程内存的变量，因为应用可能已经重启了。而且下游仍可能重复收到，幂等还是不能省。

## 8. Kafka 原理与消息队列选型

Kafka 高吞吐的本质是：**把随机小 IO 变成批量顺序 IO。** 选型的本质是：**结论来自业务约束，不来自固定的吞吐排名。**

### 8.1 分区追加日志

- Kafka 把 Topic 拆成多个分区，消息以追加方式写入分区日志。
- 分区可以分布在不同 Broker 上并行读写，这是横向扩展吞吐的基础。
- 同一消费者组内，一个分区同时只由一个消费者处理（分区数决定并发上限）。

### 8.2 批量与压缩

- 生产者把同一分区的多条记录组成批次，Broker 按批写入，消费者也批量拉取。
- 批次可以整体压缩，减少网络请求数、磁盘操作和传输字节数。
- 意义：单条消息发送会产生大量固定的协议和 IO 开销，批量把这些固定成本摊薄；消费时直接搬运存好的批次，不用逐条解包重组。

### 8.3 页缓存

- Kafka 依赖操作系统的 page cache 缓存日志页，顺序追加和线性读取减少随机磁盘寻址。
- 数据在内核页缓存里，不受 JVM 堆对象生命周期约束，服务重启后缓存仍可用。

> page cache 是操作系统用空闲内存给磁盘文件做的缓存，读写过的文件页留在内存里，下次直接用。它由内核管理、不占 JVM 堆，所以 Kafka 不自己在堆里做缓存，而是顺势借用：消费者读的大多是刚写入的新消息，这些页还在 page cache 里，直接内存命中，几乎不碰磁盘。

### 8.4 零拷贝

- 在适用的非 TLS 传输路径上，用 `sendfile` 把 page cache 里的数据直接送往网络。
- 减少用户态和内核态之间的数据复制。

> 传统方式把文件发到网络，数据要先从内核拷进用户态应用、再拷回内核 socket 缓冲，来回切换又多次复制。但 Kafka 转发消息并不需要看内容，这趟绕行是浪费。零拷贝借助操作系统的 `sendfile`，让数据在内核里直接从 page cache 送到网卡，省掉多余的拷贝和用户态/内核态切换。开启 TLS 时数据必须进用户态加解密，这条直通路径就用不了。

### 8.5 选型维度

不要只背吞吐排名，要综合看多个维度：

- 延迟、可靠性
- 路由模型
- 顺序 / 事务 / 延迟能力
- 消息保留与回溯
- 运维成本、团队经验

### 8.6 三大 MQ 的常见定位

| 中间件 | 擅长 | 典型场景 |
| --- | --- | --- |
| Kafka | 高吞吐、分区扩展、长期保留与回放 | 日志采集、事件流、实时计算数据管道 |
| RocketMQ | 事务、顺序、延迟、消费重试 | 订单、支付等业务消息 |
| RabbitMQ | Exchange + Routing Key 灵活路由 | 一条消息按多个路由键分到不同业务队列 |

### 面试问答

**Q1：Kafka 为什么吞吐量高？**

核心一句话：把随机小 IO 变成批量顺序 IO。

第一，它按分区追加写日志，顺序写盘比随机写快得多，分区还能跨 Broker 并行扩展吞吐。

第二，生产者批量发送并压缩，Broker 成批写入，消费者批量拉取，把单条消息的协议和 IO 固定开销摊薄。

第三，靠操作系统 page cache 缓存，读写走顺序访问；在非 TLS 路径上还能用 sendfile 零拷贝，少一次用户态和内核态的复制。

打个比方：一条条发一万次，就是一万次协议和 IO 开销；装成批次，一次网络往返、一次连续写就干完更多活。

**Q2：Kafka、RocketMQ、RabbitMQ 怎么选？**

我的原则是先看业务约束，再看技术栈，不背固定排名。

第一，日志采集、事件流、要长期保留和高吞吐、要消息回放的，优先 Kafka。

第二，订单、支付这类业务消息，看重事务、同订单顺序、延迟关单、消费重试的，RocketMQ 的模型更贴近。

第三，一条消息要按多个 Routing Key 分到不同业务队列、需要灵活路由的，RabbitMQ 更直观。

最后再结合现有技术栈和团队运维能力定，选型结论来自约束，不来自排名。
