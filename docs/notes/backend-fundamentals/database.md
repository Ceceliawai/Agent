# 数据库类型与选型

Redis 和 MySQL 都是单一产品的深挖，本文往上抽一层：先讲清数据库的整体分类，再横向对比各类数据库的数据模型、一致性与适用场景，最后给出选型思路。

## 1. 总分类：关系型 vs 非关系型

数据库按数据模型可分为两大支：**关系型（RDBMS）**用二维表和表间关系描述数据，强调结构化与事务；**非关系型（NoSQL）**泛指一切不以关系表为核心模型的数据库，用更灵活的结构换取扩展性与性能。

| 类别 | 数据模型 | 代表 | 定位 |
| --- | --- | --- | --- |
| 关系型 (RDBMS) | 二维表 + 表间关系 | MySQL、PostgreSQL、Oracle | 强一致、支持事务、结构化 |
| 非关系型 (NoSQL) | 多种（见第 2 节四类） | Redis、MongoDB、Cassandra、Neo4j | 高扩展、灵活 schema |

> [!TIP]
> NoSQL 的 "No" 更准确的理解是 "Not Only SQL"：它不是要取代关系型，而是在关系模型不擅长的场景（超大规模、灵活结构、特殊访问模式）里作为补充。

## 2. 非关系型的四大类

NoSQL 内部按数据模型分为四大家族，彼此定位差异很大，不能笼统混谈。

### 2.1 键值型（Key-Value）

用哈希表存储 `key → value`，value 对数据库不透明，只按 key 存取。以极简结构换极致读写性能，适合缓存、会话、计数器等场景。代表：**Redis**、Memcached、DynamoDB。

**Redis** 是基于内存的键值数据库，常用作缓存、分布式锁、计数器、排行榜。数据主要在内存中读写、避免磁盘 IO，核心命令单线程串行执行，靠 I/O 多路复用扛住海量连接。它不只是简单 KV，value 支持 String/Hash/List/Set/ZSet 等多种结构；为防宕机丢数据，提供 RDB 快照和 AOF 日志两种持久化。定位是关系型数据库之上的加速层，而非持久化主库。

### 2.2 文档型（Document）

以 JSON/BSON 文档为存储单位，字段可嵌套、schema 灵活，天然贴合业务对象。适合结构多变的实体，如用户资料、商品、订单快照。代表：**MongoDB**、CouchDB、**Elasticsearch**。

**MongoDB** 是面向文档的数据库，数据按文档存储、文档可嵌套且字段不固定（灵活 schema），免去关系型频繁改表；物理上文档归入 collection（相当于表）。查询靠 B 树索引，支持二级索引；靠分片（Sharding）做水平扩展、副本集（Replica Set）做高可用；事务以单文档原子为主，新版也支持多文档事务。

**Elasticsearch** 是基于 Lucene 的分布式搜索引擎，数据模型属文档型，但核心定位是全文检索与聚合分析，常用于日志检索、站内搜索。它的核心是倒排索引——不存"文档→内容"，而存"词→哪些文档包含它"，因此能极快地按关键词查文档；写入时对文本分词建倒排索引，数据切成多个 shard（分片）分布到集群、每个 shard 有副本保证高可用。它擅长"搜"，但一致性偏弱（近实时），通常不做业务主库。

### 2.3 列族/宽列型（Column-Family / Wide-Column）

按列族组织数据，适合稀疏表和超高写入吞吐，横向扩展能力强。适合日志、时序、大数据分析等海量写入场景。代表：**Cassandra**、HBase、Bigtable。

### 2.4 图型（Graph）

以节点 + 边直接表达实体和关系，擅长多跳关联查询，避免关系型多表 JOIN 的性能塌陷。适合社交网络、风控关系链、推荐。代表：**Neo4j**、JanusGraph。

**Neo4j** 是图数据库，数据模型是属性图：节点（实体）、边（关系）、两者都能带属性。关键在免索引邻接——每个节点直接存着指向邻居的物理指针，查关系时顺指针走即可，不用像关系型那样多表 JOIN，因此"查某人朋友的朋友"这类多跳查询性能碾压关系型。查询语言是 Cypher（类似图版 SQL）。

## 3. 横向对比

把关系型和四类 NoSQL 放在一起对比，选型时按这几个维度权衡。

| 维度 | 关系型 | 键值型 | 文档型 | 宽列型 | 图型 |
| --- | --- | --- | --- | --- | --- |
| 数据模型 | 二维表 + 关系 | key → value | JSON/BSON 文档 | 列族 | 节点 + 边 |
| Schema | 固定、强约束 | 无 | 灵活 | 灵活 | 灵活 |
| 事务 | 强（ACID） | 弱/单 key | 单文档为主 | 弱 | 部分支持 |
| 关联查询 | JOIN 强 | 不支持 | 弱（需冗余） | 弱 | 多跳最强 |
| 水平扩展 | 较难 | 强 | 强 | 极强 | 一般 |
| 典型代表 | MySQL、PostgreSQL | Redis、Memcached | MongoDB | Cassandra、HBase | Neo4j |
| 适用场景 | 事务、强一致业务 | 缓存、计数、会话 | 灵活对象存储 | 海量写入、时序 | 关系网络分析 |

## 4. 选型方法论

选型不是比"谁更强"，而是**由业务约束反推**：先看数据结构和访问模式，再看一致性与扩展性要求。

- **需要事务与强一致**（交易、账户、订单）：选关系型，MySQL/PostgreSQL 是默认答案。
- **要极致读写性能做缓存/计数/会话**：选键值型 Redis，通常作为关系型之上的加速层，而非唯一存储。
- **数据结构多变、迭代快**（内容、配置、画像）：选文档型 MongoDB，省去频繁改表。
- **海量写入、按时间/大宽表存**（日志、监控、时序）：选宽列型 Cassandra/HBase。
- **核心诉求是关系与多跳查询**（社交、风控、推荐）：选图型 Neo4j。

> [!TIP]
> 现实系统往往是**组合使用**（Polyglot Persistence）：MySQL 存核心业务数据、Redis 做缓存、ES 做搜索、Cassandra 存日志。不要试图用一种数据库解决所有问题。
