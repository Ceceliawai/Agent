# 工具调用

Agent Loop 里模型会调用工具，但模型输出一个 Tool Call，并不等于某个函数就直接被执行了。

模型做的是提出一个行动请求：调用哪个工具、参数是什么。真正决定“能不能执行、在哪里执行、执行完把什么结果交回去”的，是 DSH 的工具调用管线。

## 1. 先看工具调用涉及哪些事件

一条 Tool Call 会经过几类事件。可以先把它们理解成不同阶段的检查点：有的负责记录事实，有的负责判断能不能执行，有的负责包裹真正的工具调用，还有的负责把结果整理成统一格式。

| 事件 / 阶段 | 什么时候发生 | 主要做什么 | 需要检查什么 |
| --- | --- | --- | --- |
| `tool/call` | 模型产生 Tool Call 之后 | 先把模型的行动意图写入 Session | 工具名、调用 ID、参数等基本信息是否能被记录 |
| `tools/pre-execute` | 工具主体执行之前 | 依次执行准入、权限、Sandbox 和审批逻辑 | 工具是否存在、当前 Agent 是否可见、参数是否合理、权限是否允许、是否需要用户审批 |
| `tools/execute` | 通过执行前检查之后 | 包裹并调度工具主体 | 执行环境、超时、取消、重试和异常处理是否满足策略 |
| 工具主体 | `tools/execute` 责任链中 | 真正执行文件、命令、网络或其他业务动作 | 工具自己的业务校验和运行结果 |
| `tools/post-execute` | 工具主体返回之后 | 加工原始结果，并决定哪些内容可以继续向后传递 | 结果是否需要过滤、替换、补充，异常是否要统一转换 |
| `tools/result` | 最终结果生成之后 | 通知 UI 和其他插件工具已经完成 | 结果是否已经规范化、是否与原始 Tool Call 对应 |
| `tool/result` | `tools/result` 之后 | 把唯一的最终结果写入 Session | 调用和结果是否配对，后续是否可以恢复和回放 |

它们之间的关系可以简单画成这样：

```text
tool/call
  ↓ 记录模型意图
tools/pre-execute
  ↓ 做准入、权限和审批校验
tools/execute
  ↓ 包裹执行环境与运行策略
工具主体
  ↓ 返回原始结果
tools/post-execute
  ↓ 做结果校验、过滤和规范化
tools/result → tool/result
  ↓
UI、Trace 与下一次模型请求继续消费
```

这里需要特别注意：`tool/call` 和 `tool/result` 是 Session 中真正留存的事件；`tools/pre-execute`、`tools/execute`、`tools/post-execute` 更像执行过程中的 Hook / Waterfall。前者记录“发生了什么”，后者决定“这件事怎样被允许和处理”。

## 2. 为什么不能直接调用函数

如果模型输出直接连接到工具函数，很多业务问题都没有统一的处理位置：

- 这个工具是否对当前 Agent 可见？
- 当前用户是否有权限执行？
- 是否需要用户审批？
- 工具应该在本地还是 Sandbox 中运行？
- 超时、重试、取消应该由谁负责？
- 工具调用和结果怎样写进 Session，保证恢复之后还看得懂？

所以 DSH 把“模型提出意图”和“系统执行动作”拆开。模型只负责表达 Action，Harness 负责对这个 Action 做约束和落账。

## 3. 工具调用的整体流程

```text
模型产生 Tool Call
→ 先写入 tool/call
→ tools/pre-execute
→ 权限守卫与可选审批
→ tools/execute
→ 工具主体
→ tools/post-execute
→ 结果规范化
→ 写入唯一的 tool/result
→ UI 与下一次模型请求继续消费
```

这条链路中，前半段是在判断和准备，真正的工具主体只是其中一环。

## 4. 先记录调用意图

模型产生 Tool Call 以后，系统会先写入 `tool/call` SessionEvent，再开始执行。

这一步看起来有点反直觉：工具还没执行，为什么先写日志？

因为 Tool Call 本身就是一个需要留存的事实。即使进程在工具执行期间崩溃，恢复逻辑也能知道：模型已经要求执行这项操作，但结果还没有完成。

所以工具调用在执行之前就已经有了一个可审计的起点：

- UI 可以显示“正在执行哪个工具”；
- 恢复逻辑可以识别未完成的调用；
- Trace 可以把模型决策和工具动作对应起来；
- 压缩时也知道这是一组不能随便拆开的事件。

## 5. 执行前：准入、权限与审批

`tools/pre-execute` 是工具真正执行前的 waterfall。很多插件都会在这里参与。

### 5.1 工具是否允许进入执行阶段

首先要判断当前 Tool Call 是否满足基本条件：

- 工具是否已经注册；
- 工具是否对当前 Agent Scope 可见；
- 参数是否符合工具要求；
- 当前 Agent 是否处于允许执行工具的状态。

如果不满足，工具不会进入主体执行阶段，而是生成一个明确的拒绝结果。

### 5.2 权限守卫是单调的

权限和安全策略也在这个阶段处理。这里有一个重要规则：**守卫只能增加限制或拒绝，不能降低前面已经施加的约束。**

比如上层 Scope 已经要求某个文件操作必须经过审批，下面的插件不能把它改成无条件放行。这样不同层级的安全策略叠加起来，才不会因为某个后置插件而失效。

### 5.3 可选的用户审批

对于删除文件、执行命令或访问受限资源等操作，插件可以要求用户审批。审批本身不是工具业务逻辑，而是一次“是否允许继续”的决策。

如果用户拒绝，后续不会调用工具主体，但 Session 仍然会记录这次拒绝，让模型和 UI 知道这次 Action 为什么没有发生。

::: info 守卫的职责
守卫只回答“允许还是拒绝”，不负责伪装成工具结果。把权限决策和工具业务结果分开，后续恢复、审计和模型解释都会更清楚。
:::

## 6. 执行中：调用工具主体

通过 `tools/execute`，插件可以在工具主体外包裹一些通用逻辑，比如：

- 超时控制；
- 重试；
- 取消信号；
- 指标统计；
- Sandbox 或远程执行环境；
- 统一的错误捕获。

工具本身只需要完成自己的业务动作，不需要每个工具都重新实现一套超时、重试和监控。

这个执行 waterfall 也允许某个插件在必要时接管执行。例如本地工具可以被转发到远程 Sandbox，但无论最后由谁执行，结果都要回到同一条规范化流程中。

## 7. 执行后：处理工具结果

工具主体返回的原始内容，不一定适合直接交给模型。`tools/post-execute` 会对结果做最后处理。

插件可以在这里：

- 接受原始结果；
- 阻止不应该暴露的内容；
- 把结果替换成更适合模型消费的表达；
- 追加必要的上下文说明；
- 把异常统一转换成失败结果。

处理完成后，系统会把成功、失败、拒绝、超时和取消等情况规范成统一的结果结构，并通过 `finalizeContent` 生成最终内容。

## 8. 只保留一个最终结果

工具执行完成后，系统会通知 `tools/result`，并写入唯一的一条 `tool/result` SessionEvent。

为什么强调“唯一”？

因为 UI 和下一次模型请求不能各自解释一遍原始返回值。它们都应该从同一个最终结果继续：

```text
原始工具返回值
→ post-execute 加工
→ finalizeContent 规范化
→ 唯一 tool/result
→ UI 展示 + 下一次模型上下文
```

这样即使某个插件替换了结果，模型、页面和恢复逻辑看到的也仍然是同一件事。

## 9. Tool Call 与 Tool Result 必须配对

工具历史不能只看到一次调用，却不知道它最后成功、失败还是被中断。

因此：

- Tool Call 在执行前落账；
- Tool Result 在执行完成后落账；
- 崩溃恢复时可以识别缺失结果的调用，并补齐终止语义；
- 上下文压缩选择历史范围时，也不能从一组调用和结果的中间切开。

这也是工具调用可以被恢复、回放和审计的原因。

## 10. 为什么把工具管线做成插件

Agent Loop 只需要知道“这个 Step 里有一批 Tool Call 需要处理”，不需要把每一种工具、权限和执行环境都写进主循环。

以后增加新的 Sandbox、审批规则或工具观测能力时，只需要挂进工具管线，不需要改变模型请求和 Turn 收敛的基本逻辑。

::: tip 章节小结
Tool Call 是模型提出的行动请求，工具管线才是 Harness 对这个行动负责的地方。它把一次模型意图，转化为经过准入和约束、可以执行、结果唯一、并且能够恢复的 Session 事实。
:::
