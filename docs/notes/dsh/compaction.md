# 上下文压缩

Agent 的 Session 会不断变长，但是模型的上下文窗口是有限的。所以运行一段时间之后，系统总会遇到一个问题：历史还在，但模型已经不能把全部历史都放进下一次请求了。

DSH 的压缩模块要解决的不是简单地“删掉旧消息”，而是：在不丢失原始事实的前提下，减少模型下一次需要读取的内容。

## 1. 先给结论：动作是两段，路径不止两种

如果按照“实际做了什么压缩动作”来分，DSH 是两段式的；但如果按照“什么时候、以什么策略进入压缩”来分，就不能简单说只有两级。

1. **第一级：工具结果剪枝**。优先处理体积很大的旧工具输出，尽量不改变对话结构；
2. **第二级：历史摘要替换**。如果剪枝之后仍然不够，就选择一段安全的旧历史生成摘要，用摘要替换 Model Surface 中的那段内容。

所以它不是一上来就总结整段对话，而是先做成本更低、影响更小的处理。只有第一级释放的空间不够，才会进入第二级。这里的“二级”描述的是压缩动作，不代表整个模块只有两条运行路径。

### 1.1 触发位置和相关事件

压缩通常发生在下一次模型请求之前，也就是 `agent/pre-step` waterfall 中。可以先通过下面这张表理解每个位置要做什么：

| 位置 / 事件 | 什么时候发生 | 主要检查 | 处理结果 |
| --- | --- | --- | --- |
| `agent/pre-step` | 每个 Step 准备请求时 | Token 是否接近上下文上限 | 触发自动压缩，或者直接继续请求 |
| `tokenMeter` | `agent/pre-step` 检查压力时 | 消息、工具 Schema 和运行上下文一共占多少 Token | 为后续选择压缩级别提供依据 |
| `compaction/prune` | 第一级剪枝发生时 | 哪些旧工具结果超过保留预算，且仍在当前 Model Surface 中 | 追加经过剪短的工具结果，重新测量 |
| `compaction/start` | 真正开始摘要前 | 当前 Session 是否已有未结束的压缩操作 | 建立一次压缩的锁和开始记录 |
| `compaction/summary` | 摘要模型返回之后 | 摘要是否生成成功、覆盖范围是否安全 | 保存摘要、覆盖范围和摘要调用信息 |
| `user/message(surfaceOp: replace)` | 摘要准备写回表层时 | Tool Call / Tool Result 是否完整配对，替换范围是否有效 | 让摘要替换 Model Surface 中的旧历史 |
| `compaction/end` | 压缩流程结束时 | 这次压缩是成功还是失败 | 释放压缩锁，记录最终状态 |
| `agent/request-error` | 模型已经返回上下文溢出时 | 这次错误是否属于可恢复的 Context Overflow | 走压缩后重试，而不是直接结束 Turn |

这里有一个容易混淆的地方：`compaction/start`、`compaction/summary` 和 `compaction/end` 都是 Session Log 中的记录事件，它们本身不会直接进入模型上下文；真正改变 Model Surface 的，是带 `surfaceOp: replace` 的 `user/message`。

### 1.2 三种触发方式，不等于三种压缩级别

从“什么时候触发”来看，压缩又有三种入口：

- **自动压力触发**：在 `agent/pre-step` 发现 Token 压力过高；
- **溢出恢复触发**：模型请求已经因为上下文溢出失败，在 `agent/request-error` 中补救；
- **手动触发**：用户执行 `/compact`，对当前历史主动做一次压缩。

这三种入口最后可以复用同一个压缩引擎。也就是说，触发方式有三种，但压缩动作本身仍然按照“先剪枝、再摘要”的两段策略执行。

### 1.3 压力路径还可能进行多轮摘要

在正常的压力压缩中，摘要并不一定只执行一次。系统会在摘要替换之后重新测量 Token：

- 如果已经低于阈值，就结束这次压缩；
- 如果仍然高于阈值，就按照 `compactionRetries` 再尝试下一段历史；
- 默认配置允许首次压缩之外再进行一次尝试。

这属于同一级摘要动作的多轮重试，不是新增了“第三级压缩”。所以更准确的说法是：**两段压缩动作 + 三种触发入口 + 压力场景下可配置的多轮摘要。**

另外，上下文溢出恢复和手动 `/compact` 有自己的边界：

- `agent/request-error` 收到模型确认的上下文溢出后，会绕过正常压力阈值和近期保留策略，强制寻找一次可以配对、可以缩小的平衡范围；
- `/compact` 可以在没有达到压力阈值时主动执行，通常要求 Agent 处于空闲状态；
- 它们仍然复用“剪枝 → 摘要替换”的动作，但不能和正常 `agent/pre-step` 压力路径混为一谈。

## 2. 自动压缩的触发位置

压缩是一个可选的插件能力，不属于 Agent Loop 的主干。

自动压缩通常在 `agent/pre-step` 中检查 Token 压力。因为这个位置正好在下一个模型请求之前，所以压缩完成后可以直接影响当前 Step 要看到的 Model Surface。

如果模型已经明确返回“上下文溢出”，系统也可以在 `agent/request-error` 中触发恢复，再重新发起请求。

手动执行 `/compact` 和自动压缩使用的是同一套能力，避免手动和自动形成两种不一样的压缩逻辑。

## 3. 自动压缩的整体流程

```text
agent/pre-step 检查 Token 压力
├── 未超过阈值 → 不做压缩，继续请求模型
└── 超过阈值
    → 先尝试剪枝工具结果
    → 重新测量 Token
    ├── 已经低于阈值 → 结束压缩，继续请求模型
    └── 仍然过高 → 选择安全历史范围
        → 调用模型生成摘要
        → 写入 compaction/summary
        → 用摘要替换 Model Surface
        → 重新测量，必要时再进行下一轮摘要

agent/request-error 收到上下文溢出
→ 绕过正常阈值和保留尾部策略
→ 剪枝并寻找一次平衡的可压缩范围
→ 摘要替换
→ 重新请求原模型调用
```

## 4. 第一级：先剪枝工具结果

工具结果经常比普通对话更占空间，特别是文件内容、命令输出和长列表。

这些内容有时已经被后续的模型回答吸收，继续完整放在每一次请求里，成本比较高。因此压缩会先尝试剪枝旧的工具结果，再重新测量 Token。

如果剪枝已经释放了足够空间，就不需要生成一段完整的对话摘要。这是一种影响比较小的处理方式：保留对话结构，只缩短已经不太需要原样展示的工具内容。

## 5. 第二级：选择可以压缩的历史范围

如果剪枝之后空间仍然不够，系统才会进一步选择历史范围生成摘要。

这里不能机械地截取“最早的前 N 条消息”，因为工具调用有自己的结构。一个 Tool Call 和它对应的 Tool Result 需要完整配对，不能从中间切开。

选择范围时还需要避开当前正在执行的部分，只处理已经完成、可以稳定归纳的历史。否则摘要可能把一个还没有结果的工具调用描述成已经完成。

可以把这一步理解为：

```text
找到比较旧的历史
→ 检查消息是否完整
→ 检查 Tool Call / Tool Result 是否配对
→ 避开当前正在运行的 Step
→ 确定可以交给摘要模型的范围
```

## 6. 生成摘要并替换表层

确定范围之后，系统会调用模型生成摘要，并记录压缩过程：

- `compaction/start`：开始一次压缩；
- `compaction/summary`：保存生成的摘要；
- `compaction/end`：压缩完成或结束。

然后系统会追加一条带有 `surfaceOp: replace` 的 `user/message`，告诉消息派生逻辑：摘要可以在模型表层替换之前那段历史。

下一次生成模型请求时，模型看到的就会变成：

```text
压缩摘要
+ 最近仍然需要的完整消息
+ 新到达的用户输入和工具结果
```

## 7. 替换的是 Model Surface，不是 Session Log

这里最容易混淆的一点是：压缩不会删除原始事件。

DSH 实际上有两层历史：

```text
Session Event Log
└── 完整、只追加的权威事实

Model Surface
└── 下一次请求实际展示给模型的历史投影
```

带 `surfaceOp: replace` 的消息，只改变 Model Surface。被摘要覆盖的旧事件仍然留在 Session Log 中，以后仍然可以用于：

- 回放完整过程；
- 审计某次模型决策；
- Fork 一个新的 Agent；
- 排查摘要是否遗漏了信息；
- 重新派生其他查询视图。

::: tip 这不是删除聊天记录
压缩减少的是模型的认知负担，不是系统的事实留存。即使摘要后来被发现不够准确，原始事件仍然在权威日志中，没有被永久删除。
:::

## 8. 压缩过程也需要可恢复

压缩本身也可能被中断，比如摘要请求还没有返回时进程退出。因为压缩的开始、摘要和结束都会写入 Session Log，所以恢复时可以检查是否存在只有 `compaction/start`、却没有完成事件的记录。

这时系统可以识别出一次未完成的压缩，而不是把它当作普通历史继续使用。

同样地，当模型请求确认上下文溢出时，也可以走“压缩后重试”的路径，而不是让整次 Turn 直接失败。

## 9. Token Meter 的作用

压缩是否发生，需要先知道当前请求到底有多大。Token Meter 负责估计：

- 当前 Model Surface 中的消息；
- 当前可见的工具 Schema；
- 其他会进入模型请求的上下文。

Compaction 根据这个测量结果选择策略。两者分开以后，更换模型或 Tokenizer 时，只需要调整计量方式，不需要重写压缩的业务流程。

::: tip 章节小结
DSH 的上下文压缩不是“删掉旧消息”，而是先尝试剪枝工具结果，再在安全边界内生成摘要，最后用替换语义改变模型看到的表层。原始 Session Log 一直保留，所以 Agent 可以继续工作，系统也仍然记得发生过什么。
:::
